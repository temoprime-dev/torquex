# Рабочий процесс: от запроса клиента до проверенного BIN

Три инструмента, которые стыкуются последовательно:

```
запрос клиента (JSON)                 профиль железа (JSON, для Stage 2)
кривая датчика MAF (JSON, для Stage 2)
        │                                        │
        └──────────► generate_patches.py ◄───────┘     проверки, отказы, обоснования
                            ▲
              maf_curve.py ─┘  (кривая MAF -> свои 256 столбцов патч-плана)
                            │
                            ▼
                     patches.json (status=READY)
                            │
                            ▼
                     calibration.py  ──► plan → CRC → запись → пост-проверка
                            │
                            ▼
                        patched.bin + report.json
                            │
                            ▼
                     delivery_note.py ──► наряд на калибровку (Markdown)
```

`generate_patches.py` отвечает на вопрос «что записывать и почему»,
`calibration.py` — «как записать безопасно». Первый ничего не пишет,
второй ничего не выдумывает: значение приходит только с обоснованием.

## 1. Запрос клиента

Формат — `MS41/examples/stage1_request.example.json`:

```json
{
  "version": 1, "customer": "example-client", "stage": 1, "ron": 95,
  "catalyst": "present",
  "intents": [
    {"id": "vmax", "kind": "vmax", "mode": "raise", "value_kmh": 250,
     "reason": "клиент просит 250 км/ч"},
    {"id": "hardcut", "kind": "hardcut", "mode": "harden", "hysteresis_rpm": 96},
    {"id": "rpm", "kind": "rpm_limit", "mode": "raise", "value_rpm": 6700,
     "acknowledge_risk": true}
  ]
}
```

`kind` определяет смысл намерения, `reason` попадает в наряд и в патч-файл,
`acknowledge_risk` требуется там, где изменение повышает нагрузку на мотор.

## 2. Что можно запланировать

| kind | куда пишет | что нужно от клиента |
| --- | --- | --- |
| `vmax` | `c_vs_max` (км/ч) | `value_kmh` или `mode: remove` |
| `rpm_limit` | `c_n_max` (об/мин) | `value_rpm`; при повышении — `acknowledge_risk` или лог-подтверждение |
| `hardcut` | `c_n_max_hys` (об/мин) | `hysteresis_rpm`, иначе берётся один сырой шаг от стока |
| `maf_curve` | вся кривая MAF (256 столбцов) | `curve_file` — документированная кривая датчика |
| `injectors` | базовая таблица впрыска `ip_tib__n__maf` (192 ячейки) | `--profile` с документированными форсунками + `--evidence` с подтверждающим логом |
| `vanos` | порог переключения VANOS (11×5 ячеек) | `--profile` (механика/автомат выбирает таблицу) + `threshold_file` с измеренным сравнением фаз |
| `launch_limiter` | `c_var_vs_max_act` + `c_vs_max` (км/ч) | `value_kmh`; при лимите < 100 км/ч — `acknowledge_risk`, при катализаторе — отказ |

Статусы намерений:

- `READY` — изменение прошло планировщик и попало в патч-файл;
- `REQUIRES_DATA` — значение неоткуда взять (нет логов, нет явного согласия);
- `REQUIRES_DATA` (с планом) — значение может дать только стенд: генератор
  печатает таблицы с адресами, секции лог-контракта и шаги стенда
  (`EVIDENCE_REQUIRED`, `TABLES_RESOLVED`, `GATE`, `NOTHING_WRITTEN`);
- `BLOCKED` — правило или планировщик отказали.

Статусы запроса целиком: `READY` (есть что записывать), `EMPTY` (нечего и
ничего не нарушено), `BLOCKED` (что-то отказано). **Патч-файл пишется только
при `READY`**, и `calibration.py` отказывается читать файл с другим статусом —
чтобы неполный наряд не ушёл в прошивку.

## 3. Отказы, которые заложены намеренно

- **Popcorn при катализаторе** — отказ, а не предупреждение: догорание в
  выпуске разрушает катализатор.
- **Поднятие отсечки без `acknowledge_risk`** — `REQUIRES_DATA`: клиент должен
  понимать рост нагрузки, а результат подтверждается логом. Второй путь —
  лог-подтверждение: если в `--evidence` лежит заполненная секция `rpm_limit`
  с `validated: true`, согласие не нужно, но в патч-файл уходит
  `evidence: log_evidence:<файл>` и `found: max_safe_rpm=…`. Пока файл — заглушка,
  не подтверждено ничего.
- **Зажигание и топливо под нагрузкой** — `REQUIRES_DATA` со структурным
  планом (см. `EVIDENCE_REQUIREMENTS_RU.md`): таблицы с адресами, какие секции
  `log_evidence` заполнить, какие шаги стенда пройти. Никаких «+X градусов по
  умолчанию».
- **Launch limiter** — реализован, но это ограничитель скорости через отсечку
  цилиндров, а не RPM-лимитер: ниже 100 км/ч требуется `acknowledge_risk`, при
  катализаторе — отказ, эскалация отключения цилиндров остаётся стоковой, и
  отчёт печатает её значения из патчимого образа (у B20/B25 30/70/110/160/200
  км/ч → 50/45/40/30/13, у B28 38/90/142/196/234 → 13/19/23/26/26).
- **Кривая MAF без файла кривой** — отказ: `maf_curve` требует `curve_file`,
  путь считается от каталога запроса. Кривая без `sensor`/`source`/`provenance`
  отвергается планировщиком (см. раздел 3a).
- **Профиль железа, не прошедший свои проверки** (M52TU, неизвестные
  форсунки и т.п.), блокирует генерацию целиком.
- **Значение, не представимое в ячейке** (например 300 км/ч в 8-битной
  `c_vs_max`) — отказ планировщика с указанием причины.

Каждое запланированное изменение несёт `evidence` (`customer_intent`),
`requires_validation: true` и `validation_hint` — что именно проверить после
прошивки. Это часть наряда, а не украшение: без проверки изменение считается
неподтверждённым.

## 4. Запуск

```bash
# запрос -> патч-файл (пишется только при READY)
python3 MS41/tools/generate_patches.py --bin stock.bin \
  --request MS41/examples/stage1_request.example.json \
  --out patches.json --report generation_report.json

# для Stage 2 добавьте профиль железа: он же даст work order и требования к логам
python3 MS41/tools/generate_patches.py --bin stock.bin --request req.json \
  --profile MS41/examples/stage2_profile.example.json \
  --measurements MS41/examples/stage2_measurements.example.json --out patches.json

# лог-подтверждение (пока — заглушка: ничего не разблокирует, только покажет,
# каких секций не хватает). Заглушка и её валидатор:
python3 MS41/tools/log_evidence.py --check MS41/examples/log_evidence.stub.json
python3 MS41/tools/generate_patches.py --bin stock.bin --request req.json \
  --evidence MS41/examples/log_evidence.stub.json

# патч-файл -> BIN с разделённым отчётом по байтам
python3 MS41/tools/calibration.py --bin stock.bin --patches patches.json \
  --out patched.bin --report patch_report.json

# независимая проверка результата
python3 MS41/tools/analyze_firmware.py patched.bin

# наряд для клиента из двух отчётов
python3 MS41/tools/delivery_note.py --generation generation_report.json \
  --patch patch_report.json --out note.md
```

Коды возврата: `generate_patches.py` — 1 при `BLOCKED`, `calibration.py` — 1
при `REJECTED`.

## 3a. Замена кривой MAF

Если в Stage 2 меняется датчик, у которого есть документированная кривая, её
раскладывает `MS41/tools/maf_curve.py`:

```bash
python3 MS41/tools/maf_curve.py --stock stock.bin --curve sensor_curve.json \
  --out maf_patches.json --report maf_report.json
```

Файл кривой обязан нести `sensor`, `source` и `provenance` (`datasheet`,
`measured` или `derived`) — иначе отказ. Кривая обязана быть неубывающей
функцией напряжения; всё, что вышло за её пределы, удерживается на краевом
значении и **считается** в отчёте (`CURVE_EXTRAPOLATED`), чтобы было видно,
какая часть переноса — допущение. Отчёт также даёт максимальное отклонение от
стоковой кривой и предупреждает `CEILING_ABOVE_STOCK`, если новый датчик
поднимает потолок расхода: тогда `c_maf_max*` надо смотреть в том же наряде.

Примеры: `MS41/examples/maf_curve_stock_b28.example.json` — стоковая кривая,
снятая из фикстуры B28 (`--dump-stock`), `MS41/examples/maf_curve_example.json`
— **пример** трансформации (+6 % выше 2 В), а не даташит реального датчика.

## 3b. Пределы по воздуху вместе с кривой

Новая кривая с более высоким потолком сама по себе ничего не даёт: пределы
нагрузки (`c_maf_max` — «Maximum air mass», `c_maf_max_diag` — порог
диагностики «short circuit to battery») остаются на месте, лишний диапазон
недостижим, а диагностика начинает срабатывать раньше. Поэтому тот же интент
`maf_curve` планирует и пределы — но только тогда, когда это доказано:

```bash
# посчитать, что было бы нужно (ничего не пишет без лога)
python3 MS41/tools/maf_limits.py --bin stock.bin \
  --curve MS41/examples/maf_curve_example.json \
  --evidence MS41/examples/log_evidence.stub.json

# с логом, подтверждающим, что стоковый датчик упирался в потолок
python3 MS41/tools/maf_limits.py --bin stock.bin --curve curve.json \
  --evidence evidence.json --out limit_patches.json --report limit_report.json
```

Правила:

- **Пропорция, а не выдуманная формула.** Пределы сдвигаются ровно на тот же
  коэффициент, на который вырос потолок кривой (в примере 725.09 → 768.60 кг/ч,
  ×1.0600). Документированной формулы «кг/ч → мг/такт» в XDF нет, поэтому
  конвертация не изобретается: сохранение отношения сохраняет стоковые запасы,
  а результат проверяется логом после прошивки.
- **Нужен лог насыщения.** Секция `maf` контракта должна говорить
  `saturated: true` и показывать правдоподобное `voltage_max_v` (≥ 4.5 В, сетка
  доходит до 5.018 В). Иначе `SATURATION_NOT_PROVEN` и `REQUIRES_DATA`: рост
  потолка не обоснован. Без лога печатаются готовые значения и ничего не
  записывается.
- **Диагностический порог идёт за датчиком, а не за неисправностью.**
  `c_maf_max_diag` сдвигается пропорционально диапазону и помечается
  предупреждением `DIAG_LIMIT_FOLLOWS_SENSOR`; «поднять порог, чтобы не горела
  ошибка» этим инструментом сделать нельзя.
- **Рост больше 30% — отказ** (`CEILING_RISE_OUT_OF_SCOPE`): это уже другой
  проект (другой корпус ДМРВ или наддув), а не замена датчика.
- **Остальное семейство не трогается** и перечисляется в отчёте с причинами:
  `c_maf_max_ch_3` (термический предел подогрева катализатора),
  `c_maf_lam_tol_tra`, `c_maf_ti_ad_max` (пороги лямбда-адаптации),
  `c_maf_max_isa`/`c_maf_ad_isa` (холостой ход), `c_abc_max_maf` и другие.

## 3c. Порог VANOS по измеренной линии

Порог переключения VANOS (`ip_maf_min_ivvt__n__tco` — механика,
`ip_dri_maf_min_ivvt__n__tco` — автомат) это нагрузка, выше которой ЭБУ
доворачивает впускной распредвал. Новый коллектор/валы/выпуск сдвигают кривую
нагрузки, под которую порог был написан, и стоковая линия перестаёт совпадать
с точкой, где выгоднее другая фаза. Метод из наряда Stage 2: измерить нагрузку
с довёрнутым и отвёрнутым валом, найти пересечение и поставить порог туда —
никогда не копируя число и никогда не перенося таблицу с механики на автомат.

```bash
# что есть в стоке: адрес, оси, «запрещающие» ячейки — данных не требует
python3 MS41/tools/vanos_switch.py --bin stock.bin --dump-stock -

# по измеренному файлу: план ячеек и патч-файл
python3 MS41/tools/vanos_switch.py --bin stock.bin --transmission manual \
  --profile MS41/examples/stage2_profile.example.json \
  --curves measured_comparison.json --out vanos_patches.json --report vanos_report.json
```

Файл сравнения (`MS41/examples/vanos_comparison.example.json` — форма, а не
данные) требует: `engine`, `transmission`, `source`, `provenance`,
`measured_tco_c`, `crossing_rpm`, кривые `advanced`/`retarded` и линию
`threshold`. Правила:

- **`provenance` обязателен `measured`.** Линия переключения, взятая из
  даташита или выведенная пропорцией, не доказывает, что фаза стала лучше:
  `PROVENANCE_NOT_MEASURED`. Пример в `examples/` намеренно помечен `derived`
  и отвергается — в репозитории нет и не может быть измеренных чисел.
- **Пересечение проверяется по самим кривым.** Заявленный `crossing_rpm` должен
  совпасть с расчётным (допуск 10% или 200 об/мин), иначе
  `CROSSING_MISMATCH`: порог поставили бы на линию, которую никто не измерял.
- **Порог должен быть достижим.** В каждой точке он обязан лежать ниже
  измеренной огибающей (`THRESHOLD_UNREACHABLE` иначе): иначе переключение
  никогда не сработает.
- **Пишутся только «тёплые» столбцы** — те, где температура ОЖ не ниже
  `measured_tco_c`. Холодные столбцы остаются стоковыми и перечисляются в
  отчёте: поведение VANOS на холодном моторе это сознательное стоковое
  решение, а не следствие нового порога.
- **Строки «никогда не переключать» остаются такими.** Максимум таблицы
  (1301.85 мг/такт, raw 239) — это сентинел «выключено»; 15 из 55 ячеек в
  стоке такие (холодный столбец и верхняя строка 4128 об/мин). Новый порог их
  не трогает (`NEVER_SWITCH_KEPT`).
- **Обороты вне измерения не экстраполируются** — строки остаются стоковыми
  (`ROWS_OUTSIDE_MEASUREMENT`).
- Ячейки, которые уже совпадают со стоком по сырому значению, не
  переписываются (`CELLS_ALREADY_MATCH`).

Отдельно: XDF помечает эту таблицу как `°C`, хотя описание говорит «switching
threshold (air mass)», а квант равен нагрузочному (5.44706 мг/такт). Отчёт
говорит об этом (`XDF_UNITS_MISLABELLED`), и патч-файл указывает мг/такт —
единицы в патче важнее поля XDF, потому что по ним клиент читает наряд.

Гистерезис (`id_maf_hys_ivvt__n`), порог по дросселю на высокой нагрузке
(`id_pvs_ivvt__n`) и поведение VANOS на высокой нагрузке (`id_ivvt_n_fl__n`) в
политику не входят и остаются стоковыми: это отдельные решения, и наряд
перечисляет их для проверки.

## 4a. Наряд

`delivery_note.py` собирает Markdown-наряд из отчётов двух инструментов и
ничего к ним не добавляет. В наряде: хеши исходника и результата, таблица
изменений с адресами, сырыми и инженерными значениями и отклонением от стока,
отдельная таблица «почему именно эти значения» (источник значения, признак
`requires_validation`, обоснование клиента), список невыполненных пунктов с
причинами, требования к логированию, отказы и границы.

Два правила наряда:

- всё, что требует проверки, помечено как **невыполненное** — наряд строится по
  расчёту, а не по заездам; подразумевать проверку нельзя;
- статус записи называется прямо: `WRITTEN` расшифровывается как «файл записан
  на диск (в ЭБУ не записан)».

Пример результата — `MS41/examples/delivery_note.example.md` (собран из фикстуры
`MS41_1429861_E36_328i_M52B28_1997_4101_partial.bin` по запросу
`stage1_request_resolved.example.json`; в тексте остались пути песочницы, это
нормально). Пример запроса с неполным нарядом — `stage1_request.example.json`.

Пример `stage1_request.example.json` намеренно содержит popcorn при
катализаторе: он показывает, как выглядит частично выполнимый наряд — `vmax` и
`hardcut` проходят планировщик, `rpm_limit` ждёт согласия, popcorn отказан,
статус запроса `BLOCKED`, патч-файл не пишется до решения клиента.

## 5. Логи: контракт вместо ожидания

Логов MS41 у проекта нет, и это не временное состояние. Поэтому всё, что без
логов не решается, сведено в один файл-контракт, а не разбросано по коду:

```bash
python3 MS41/tools/log_evidence.py --write-stub my_evidence.json   # пустой шаблон
python3 MS41/tools/log_evidence.py --check my_evidence.json --json # проверка
```

Секции и поля (все обязаны быть заполнены целиком, иначе секция считается
пустой):

| Секция | Поля | Что разблокирует |
| --- | --- | --- |
| `rpm_limit` | `validated`, `max_safe_rpm` | подъём отсечки без `acknowledge_risk` |
| `knock` | `knock_retard_deg_max`, `rpm_at_max_knock` | будущие правки зажигания (сейчас план требований к стенду) |
| `lambda` | `afr_error_percent_max`, `wideband_available` | правки топлива под нагрузкой |
| `maf` | `voltage_max_v`, `saturated` | замена датчика и потолок расхода |
| `trims` | `stft_percent`, `ltft_percent` | связка «форсунки -> константа впрыска» |
| `injectors` | `duty_percent_max`, `maf_ceiling_kgh` | запас по скважности в Stage 2 |

Правила простые и намеренно строгие: заглушка (`kind: "stub"`) не имеет права
нести числа — заполненная заглушка отвергается с `STUB_WITH_DATA`; реальный
файл (`kind: "real"`) обязан назвать источник и каналы, из которых собран
(`EVIDENCE_SOURCE_MISSING`, `EVIDENCE_CHANNELS_MISSING`), и содержать хотя бы
одну заполненную секцию (`EVIDENCE_EMPTY`). Когда логи появятся, файл
заполняется по этому же формату — менять код не нужно: все потребители читают
одни и те же секции. Кто именно что читает — в `CALIBRATION_RU.md`.

## 6. Проверка раскладки таблиц без логов

Оси и ориентация карт проверяются без логов, по XDF и бинарнику:

```bash
python3 MS41/tools/table_layout.py --bin stock.bin            # три ключевые карты
python3 MS41/tools/table_layout.py --bin stock.bin --all      # все карты со спутниками
python3 MS41/tools/table_layout.py --bin stock.bin --json     # машинный формат
```

Инструмент доказывает, что адрес, размерность, спутники осей и ориентация
таблицы совпадают с описанием в XDF, и печатает проблемы вместо догадок.
Подробнее — в `CALIBRATION_RU.md`.

## 6a. Замена форсунок

Большие форсунки льют больше топлива за миллисекунду, поэтому базовую таблицу
впрыска надо укоротить. Инструмент считает **один** коэффициент:

```text
коэффициент = производительность стока / производительность новых
```

и не пишет ничего, пока этот коэффициент не подтверждён вторым, независимым
источником — логом с уже установленными форсунками:

```text
коэффициент из лога = 1 + LTFT/100
```

Например, сток 190 см³/мин, новые 240 см³/мин → из данных датчика 0.7917;
ECU с новыми форсунками должен снять около −20.8% топлива, то есть из лога
0.792. Расхождение больше 10% — отказ (`FACTOR_MISMATCH`): значит, врут либо
данные датчика, либо лог, и разбираться надо с этим, а не с картой.

```bash
python3 MS41/tools/injector_scaling.py --bin stock.bin \
  --profile MS41/examples/stage2_profile_injectors.example.json \
  --evidence MS41/examples/fuel_scaling.stub.json

# с логом: 192 ячейки, патч-файл, дальше обычный патчер
python3 MS41/tools/injector_scaling.py --bin stock.bin --profile profile.json \
  --evidence evidence.json --out injector_patches.json --report injector_report.json
python3 MS41/tools/calibration.py --bin stock.bin --patches injector_patches.json \
  --out patched.bin --report patch_report.json
```

Что инструмент **не** делает и говорит об этом в отчёте: не трогает
`c_ti_min_iv` (минимальное время впрыска), пусковые карты и пределы
лямбда-адаптации. Это отдельные решения, и они требуют своих логов — малых
импульсов и холодного пуска. Скважность выше 92% по логу — отказ
(`DUTY_TOO_HIGH`): масштабирование карты не лечит перегруженную форсунку.

Тот же шаг доступен из наряда: интент `injectors` в запросе клиента.

## 7. Границы

- Прошивка ЭБУ не автоматизирована: инструменты готовят BIN, запись в блок —
  отдельный аппаратный шаг.
- Калибровка делается под конкретный стоковый файл: `patches.json` хранит его
  SHA-256, а `calibration.py` отказывается патчить не прошедший свою CRC файл.
- Stage 1 в текущем виде — это ограничители и поведение на сбросе газа.
  Топливные и зажигательные карты сознательно не открыты, пока нет стенда и
  логов: см. `CALIBRATION_RU.md` и `GENERATOR_REQUIREMENTS_RU.md`.
