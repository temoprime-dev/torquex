# Stage 1 и Stage 2 для MS42: что пишется, а что ждёт данных

Инструмент: `MS42/tools/stages.py`. Он собирает файл уровня как **набор
пакетов**. Каждый пакет либо пишет значения с задокументированным источником,
либо честно сообщает `REQUIRES_DATA` и уходит в наряд как «не выполнено».
Догадок в файле не бывает.

```bash
# Stage 1 со стоковым железом: только ограничители из заявки
python3 MS42/tools/stages.py --stage stage1 \
  --bin MS42/firmware/<сток>.bin \
  --request MS42/examples/stage1_request.example.json \
  --out build/stage1.bin --report build/stage1.manifest.json --note build/stage1.md

# Stage 1 с хлопками: профиль клиента отдельным файлом
python3 MS42/tools/stages.py --stage stage1 \
  --bin MS42/firmware/<сток>.bin \
  --request MS42/examples/stage1_request_popcorn.example.json \
  --popcorn MS42/examples/popcorn.example.json \
  --out build/stage1_popcorn.bin --report build/stage1_popcorn.json

# Stage 2: донорская калибровка MS43 для пакета intake, впуск описан в hardware
python3 MS42/tools/stages.py --stage stage2 \
  --bin MS42/firmware/<сток>.bin \
  --request MS42/examples/stage2_request_intake.example.json \
  --donor-bin MS43/firmware/Siemens_MS43_MS430069_E46_M54B30_EU4_LHD.bin \
  --out build/stage2.bin --report build/stage2.manifest.json
```

Всё, что записывается, проходит через настоящее ядро патчинга (`calibration.py`):
границы политики, квантование, монотонность там, где нужно, пересчёт CRC и
пост-проверка. Если ядро отклоняет план — файл не создаётся.

## Stage 1 (стоковое железо)

| Пакет | Статус сейчас | Что это |
| --- | --- | --- |
| `limits` | **пишется** | ограничитель скорости, ограничитель оборотов (MT или AT, по передачам), гистерезис отсечки на сбросе газа — всё из заявки клиента |
| `overrun_pops` | **пишется по профилю клиента** | хлопки на сбросе газа: `--popcorn <профиль>`; без письменного подтверждения «катализатора нет» и плана дорожной проверки пакет остаётся `REQUIRES_DATA` |
| `idle` | ждёт данных | уставка холостого хода правится вместе со скважностью РХХ (иначе регулятор упрётся в предел) — нужен лог холостого хода |
| `ignition` | ждёт данных | карты RON91/RON98: стенд, лог детонации, широкополосная лямбда |
| `fueling` | ждёт данных | карты длительности впрыска: широкополосная лямбда, топливные коррекции, скважность |
| `octane` | **выбор клиента** | профиль топлива RON91/RON95/RON98 (поле `octane` или намерение `{"kind": "octane", "fuel": "ron98"}`); RON98 разрешает добавку угла (её выдаёт `ignition` и только по логу детонации), RON95/RON91 оставляют карты зажигания стоковыми |
| `disa_off` | ждёт данных | фиксация заслонки DISA: код положения задаёт клиент по механике, диагностика — отдельным слоем; нужны подтверждение механики и лог до/после |
| `isa_off` | ждёт данных | обход клапана холостого хода: без заглушки канала ХХ холостой ход глохнет; нужны лог ХХ и решение по коду ошибки |
| `fan_thermostat` | ждёт данных | трек-режим вентилятора и электронного термостата: объекты ECF/ECT у MS42 есть, но нужен клиент с трек-сценарием и границы по температуре |

`limits` без заявки не пишется: если в запросе нет ни одного намерения по
ограничителям, пакет сообщает «в заявке нет намерений» и файл не собирается
(статус `EMPTY`), а не подставляет «типовые» значения.

### Октан-профиль и опции варианта 1

Профиль топлива — это ответ на вопрос «на каком бензине машина будет ездить»,
а не пакет байтов. Обоснование — `docs/VARIANT1_WEB_ANALYSIS_RU.md` §7: у MS42
(как и у MS43/MS45) база считается по двум картам, RON91 и RON98, с
интерполяцией по выученному октану. Поэтому:

* **RON98** — добавка угла разрешена, но только через пакет `ignition` и только
  с логом детонации; карта RON91 не трогается и остаётся защитным полом;
* **RON95** — карты зажигания остаются стоковыми (ЭБУ сам интерполирует между
  91 и 98), добавка не пишется;
* **RON91** — то же самое плюс консервативный режим: работает штатная защита по
  детонации.

Запрошенная добавка угла на RON91/RON95 — это отказ до планирования
(`OCTANE_PROFILE_NO_ADDITION`), файл не выпускается. Неизвестное топливо и
противоречие «поле заявки и намерение не совпадают» — тоже отказ
(`OCTANE_PROFILE_UNKNOWN` / `OCTANE_PROFILE_CONFLICT`). Профиль попадает в
манифест (`octane`) и в наряд.

Опции `disa_off`, `isa_off`, `fan_thermostat` сегодня честно ждут данных: у
каждой в манифесте есть поле `requirements.why` (почему нельзя выпустить) и
`requirements.needs` (что должен дать клиент) — формулировки лежат в
`tools/variant1.py` и выписаны из веб-анализа §5/§6/§8. **Launch control** на
MS42 недоступен: патча программы для MS42 не существует, а таблицы лимиттера по
передачам — это отдельное намерение `launch_limiter`, и оно требует лога
(отказ `INTENT_UNAVAILABLE`, а не молчаливое игнорирование).

## Stage 2 (комбинация железа обязательна)

Stage 2 без блока `hardware` в заявке отклоняется целиком (`HARDWARE_REQUIRED`):
файл привязан к конкретной комбинации (кузов, мотор, впуск, форсунки, ДМРВ,
выпуск, валы), а не к названию. Комбинация и идентификатор набора (`dataset_id`)
попадают в манифест — по ним файл и опознаётся.

| Пакет | Статус | Условие записи |
| --- | --- | --- |
| `limits` | **пишется** | как в Stage 1 |
| `injectors` | **пишется по документу** | профиль форсунок (`--injectors`) |
| `maf` | **пишется по документу** | файл кривой (`--maf-curve`) |
| `intake` | **пишется с донорской калибровки MS43** | `--donor-bin <MS43 512K>`; перенос идёт только по явному каталогу `MS42/donor/ms43_to_ms42.json`, каждая ячейка получает источник `donor_ms43:<dataset>:<символ>` |
| `cams` | ждёт данных | паспорт валов + измеренное сравнение фаз |
| `exhaust` | ждёт данных | off-road декларация и решение по задним зондам |

### Масштабирование форсунок (MS4X)

Профиль — `MS42/examples/injectors.example.json` (это **шаблон формата**, а не
паспорт; поля `stock_flow`, `new_flow`, `source` обязательны, `dead_time_ms` —
8 значений кривой задержки по напряжению):

* множитель `f = stock_flow / new_flow`; для 190 → 240 это 0.7917;
* умножаются **только** карты длительности впрыска (9 объектов, включая
  предпусковую и прокруточную) — обогатительные множители не трогаются;
* `ip_ti_add_dly__vb` берётся из паспорта новых форсунок;
* `ip_fco_map_cor__pq_ main_col` делится на тот же множитель, чтобы расходомер
  приборки остался честным;
* отношение потоков ограничено 0.5..2.0: за этими пределами это уже не замена
  форсунок, и инструмент отказывается.

После прошивки обязательны логи: лямбда-интеграторы в пределах ±5 %, скважность
форсунок не выше ~90 %, показания расхода топлива.

### Кривая ДМРВ

Файл: `kind = "maf_curve"`, 256 значений `values_kg_h`, `provenance` обязан
начинаться с `documented_curve:` и называть даташит или стенд. Кривая должна
быть неубывающей и внутри 0..1023.98 кг/ч. Правка скейла MAF смещает нагрузку
примерно в 30 таблицах — поэтому она привязана к замене датчика, а не к «тюнингу».

### Хлопки на сбросе газа: полосы и ворота

Хлопки — это не «пресет», а профиль клиента, который проверяется по полосам.
Инструмент (`MS42/tools/popcorn.py`) принимает только два уровня громкости:

| Полоса | Порог отсечки | Угол | Задержка отсечки |
| --- | --- | --- | --- |
| `light` | +0..600 об/мин | −6..0° | 0..1.2 с |
| `medium` | +0..2000 об/мин | −12..0° | 0..3.0 с |

Агрессивный публичный пресет не предлагается: значения `aggressive`, `extreme`,
`flames`, `gunshots` отклоняются по имени, а числа вне полосы — по значению.
Это прямое требование продукта (`MEMORY.md` §5): хлопки запрещены на машинах с
катализатором, публичного злого пресета нет.

Обязательные ворота профиля:

* `no_catalyst` — письменное подтверждение (не короче 10 символов), что
  катализатора нет; строка попадает в каждое изменение как
  `customer_intent:no_catalyst=...` и в манифест;
* `thermal_watch: true` — согласие следить за температурой выпуска и
  охлаждающей жидкости;
* `road_validation_plan` — описание первых заездов (какие передачи, сколько
  минут, кто следит за температурой, на какой файл откатываться).

Пишутся обе семьи таблиц — с кондиционером и без (`ip_iga_puc__n__tco` и
`ip_iga_accin_puc__n__tco`), чтобы поведение не зависело от включённого
кондиционера. Задержка `ip_t_puc_deacc__n__maf_mmv` заполняется одним
значением по всей таблице. Каждое значение прижимается к сетке объекта
полушагом вверх (порог — 32 об/мин), поэтому запрошенные +400 об/мин дают
ровные +416 по всем колонкам, и это видно в манифесте и наряде.
Примеры результата: `examples/stage1_popcorn_manifest.example.json` и
`examples/delivery_note_stage1_popcorn.example.md`.

### Ограничитель оборотов: потолок масляного насоса

`limits` пишет мягкий и жёсткий ограничитель по передачам, требует явно указать
коробку (`manual`/`auto`) и подтверждение риска при подъёме выше стока. Сверх
этого: выше **6750 об/мин** требуется отдельное подтверждение
`acknowledge_oil_pump` (после `acknowledge_risk`). Причина не в софте — таблицы
представимы до 8160 об/мин, — а в том, что штатный масляный насос и клапанный
механизм рассчитаны на заводской предел, а измерений, доказывающих безопасный
подъём, в репозитории нет.

### Перенос карт с донорской калибровки MS43

Подробности — `MS42/docs/DONOR_MS43_RU.md`. Коротко: каталог переносов
`MS42/donor/ms43_to_ms42.json` перечисляет пары «символ MS42 ← символ MS43»
руками, с обоснованием и режимом (`direct` — пишется, `reference` — только по
явному `hardware.use_donor_references`). Инструмент проверяет базовый адрес
донора (из `BASEOFFSET` в XDF и по физической правдоподобности двух известных
объектов), форму, шкалу, порядок байт и границы политики. Несовпадение шкалы —
отказ вслух, а не «похожее» значение: `c_maf_hys_vim` в MS42 5.44706 мг/такт на
шаг против 10.8941 в MS43.

## Квантование: почему у трёх таблиц отдельный допуск

Правило ядра — «запрошенное значение должно быть представимо с точностью 1 %».
У таблиц `ip_ti_slow_wf_thd_min__tco`, `ip_ti_fast_wf_thd_min__tco` и
`ip_ti_add_dly__vb` шаг 0.032 мс, поэтому для значения 0.2 мс относительная
ошибка округления достигает 4 %, хотя абсолютная не превышает половины шага
(0.016 мс). Для этих трёх объектов политика задаёт **явный** допуск 10 %
(`max_quantization_error_percent`) с пояснением в поле `note`; остальные
объекты живут по общему правилу 1 %.

## Что попадает в манифест и наряд

Манифест (`--report`) содержит: стадию, статус, идентификатор набора, `OSID`,
тип образа, версию политики, комбинацию железа, статусы всех пакетов с
обоснованиями, список изменений, SHA-256 до/после, число изменённых байтов
значений и CRC, результат проверки контрольных сумм и пустой список
`unplanned_byte_changes`.

Наряд (`--note`) — тот же документ для клиента: что сделано, какие значения и
откуда, что не выполнено и почему, что проверить после прошивки, и статус
проверки «НЕ ВЫПОЛНЕНА».

## Проверки

`MS42/tests/test_stages.py` (38 тестов) проверяет, в частности:

* Stage 1 пишет файл, который проходит `checksum.py`, и ни один символ
  зажигания/топлива/холостого хода/хлопков в план не попадает;
* Stage 2 без железа, без профиля форсунок и без кривой ДМРВ не пишет их;
* математика масштабирования (впрыск × f, расход ÷ f) сверяется с ядром;
* файл, отклонённый ядром, на диск не попадает;
* сборка детерминирована: два одинаковых запуска дают одинаковый SHA-256;
* профиль форсунок и кривая ДМРВ валидируются (источник, диапазон, длина,
  монотонность);
* профиль хлопков без письменного подтверждения, плана проверки, полосы или с
  агрессивной интенсивностью отклоняется до всякой записи;
* донорский перенос проверяется на подменённом `BASEOFFSET` (отказ), на
  несовпадении шкалы, формы и порядка байт, на символе вне политики;
* подъём отсечки выше 6750 об/мин без `acknowledge_oil_pump` не пишется, а
  несогласованность «мягкий выше жёсткого» сообщается раньше, чем запрос
  подтверждений.

## Что осталось за пределами

Мощность в наряд не попадает: у нас нет стендовых данных, а рыночные «+5–10 /
+10–15 л.с.» — это ожидания продавцов, а не измерение конкретной машины.

Ждут замеров (и остаются `REQUIRES_DATA`): `idle` (лог холостого хода),
`disa_off`/`isa_off`/`fan_thermostat` (механика клиента, лог до/после, границы
по температуре),
`ignition`/`fueling` (стенд, детонация, широкополосная лямбда), `cams` (паспорт
валов и измеренное сравнение фаз), `exhaust` (off-road декларация и решение по
задним зондам). Это не «недоделка»: без данных генератор не имеет права
подставлять числа.
