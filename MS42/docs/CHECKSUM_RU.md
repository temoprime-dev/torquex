# CRC16 в Siemens MS42 — что именно считать и где это лежит

Документ описывает алгоритм, который реализован в `MS42/tools/checksum.py` и
`MS42/tools/analyze_firmware.py`. Всё ниже проверено на всех 16 стоковых
образах из `MS42/firmware` (15 уникальных файлов, одна пара байт-в-байт
совпадает). Ничего из MS41 сюда не переносилось: у MS41 другая схема
(цепочка указателей), она к MS42 неприменима.

## 1. Алгоритм

CRC-16/ARC: полином `0x8005`, отражённая форма `0xA001` (сдвиг вправо), начальное
значение — **своё для каждой записи** (seed), xor на выходе отсутствует, порядок
байта — младший вперёд (little endian).

```text
TABLE[b] = b, затем 8 раз: c = (c >> 1) ^ 0xA001 если c & 1, иначе c >> 1

crc16(data, seed):
    crc = seed
    для каждого байта v:
        crc = (crc >> 8) ^ TABLE[(crc ^ v) & 0xFF]
```

Табличная и побитовая реализации сверяются тестом (`test_checksum.py`,
`AlgorithmTests`), чтобы документ и код не разошлись.

## 2. Формат записи контрольной суммы

Запись описывает сама себя; её геометрия читается из образа, а не берётся из
констант:

| Смещение от начала записи | Тип | Смысл |
| --- | --- | --- |
| +0 | u16 LE | хранимая контрольная сумма |
| +2 | u16 LE | число сегментов `count` |
| +4 | `count` × (u32 LE, u32 LE) | первый и последний адрес сегмента, **оба включительно** |

CRC считается по конкатенации сегментов в объявленном порядке с seed этой
записи. Если таблица сегментов повреждена (нулевое или неправдоподобно большое
число сегментов, сегмент вне образа), это ошибка чтения, а не повод
переинтерпретировать запись.

## 3. Три записи полного образа 512 КиБ

| Имя | Адрес записи | Seed | Покрытие | Значение |
| --- | --- | --- | --- | --- |
| `boot` | `0x03C24` | `0x2D2D` | `0x00000..0x03C23` (15 396 байт) | всегда `0xDF13` |
| `cal` | `0x4FEE0` | `0x3643` | `0x48000..0x4F843` (30 788 байт) | своё для каждого образа |
| `prog` | `0x50306` | `0x3030` | 7 сегментов, 267 972 байта | всегда `0xF347` |

Сегменты `prog` (в порядке вычисления):

```text
0x500A4..0x50305
0x50342..0x52EFD
0x60000..0x60C43
0x70000..0x7EC65
0x11000..0x1FFFD
0x20000..0x2FFFD
0x30000..0x3FFFF
```

Сравнение всех 16 образов побайтово показывает: вне блока калибровки
(`0x48004..0x4F843`) и двух байт хранимой суммы `cal` (`0x4FEE0`, `0x4FEE1`)
файлы не отличаются вообще. Поэтому `boot` и `prog` — глобальные константы, а
любая правка калибровки инвалидирует только запись `cal`.

## 4. Где запись лежит в разных чтениях

| Чтение | Размер | Смещение записи `cal` в файле | Какие записи проверяются |
| --- | --- | --- | --- |
| полный образ | `0x80000` (512 КиБ) | `0x4FEE0` | `boot`, `cal`, `prog` |
| частичное чтение | `0x10000` (64 КиБ, адресная база `0x40000`) | `0x0FEE0` | только `cal` |
| чтение калибровки | `0x8000` (32 КиБ, адресная база `0x48000`) | `0x07EE0` | только `cal` |

Важно: сам адрес записи `0x4FEE0` лежит **вне** покрытия `cal`
(`0x48000..0x4F843`), поэтому пересчёт суммы не меняет данных, по которым она
считается.

## 5. Проверка и починка

```bash
# только проверка; код возврата 0 = всё сходится, 3 = есть расхождение
python3 MS42/tools/checksum.py MS42/firmware/Siemens_MS42_0110C6_E46_M52TUB28_EU3_LHD.bin

# починка в новый файл; 2 байта на каждую несовпавшую запись
python3 MS42/tools/checksum.py damaged.bin --out repaired.bin --report repair.json
```

Правила, зашитые в инструмент:

* пишутся только два байта на запись, и только в позицию хранимой суммы;
* после записи выполняется независимая повторная проверка всего файла; если
  хоть одна запись не сходится, файл не отдаётся (исключение, код возврата 4);
* если за пределами позиций сумм изменился хоть один байт, файл не отдаётся;
* непригодный размер, отсутствующая или повреждённая запись — отказ, а не
  «починка наугад»;
* отчёт JSON содержит SHA-256 до и после, старые и новые значения всех записей
  и перечень изменённых байтов.

Тот же расчёт встроен в ядро патчинга: `calibration.py` после правки значений
пересчитывает затронутые записи через `recompute_records` и отказывается
записывать образ, если проверка не прошла.

## 6. Что проверено, а что нет

Проверено:

* все 16 стоковых образов сходятся по всем трём записям без исключений;
* значения `boot`/`prog` одинаковы на всех образах, `cal` — разное;
* починка повреждённой суммы возвращает файл байт-в-байт к стоку (round-trip);
* повреждение таблицы сегментов приводит к отказу, а не к подмене CRC.

Не проверено и не утверждается:

* поведение ЭБУ после прошивки — это дорожный/стендовый шаг, а не расчёт;
* сторонние корректоры (MS4x Flasher, Chipster и т. п.) как эталон не
  использовались; у Chipster MSS5X известна ошибка в контрольной сумме
  программы, поэтому он эталоном быть не может;
* «отключение» контрольной суммы по рецепту сообщества (слово `0x4FEFE` =
  `0xFFFF` и байт `0x5002C` = `0xA8`) не применяется: это инструмент
  разработчика, а не продукт.
