# Ядро патчинга калибровки MS42

`MS42/tools/calibration.py` берёт стоковый образ MS42 и файл патча
(`{"symbol", "index", "value"}`), проверяет каждое изменение по политике
`MS42/policies/stage_policy.json`, пишет значения, пересчитывает контрольные
суммы и отдаёт новый файл **только если после записи всё сходится**.

Философия та же, что в MS41: политика — «default deny». Объект, которого нет в
allowlist, не пишется никогда, даже если он есть в XDF и значение выглядит
разумным.

## 1. Запуск

```bash
# план без записи: --out не указан
python3 MS42/tools/calibration.py --bin <сток>.bin --patches patches.json

# запись файла на диск: указан --out (файл создаётся только при статусе READY,
# прошедшем повторную проверку)
python3 MS42/tools/calibration.py --bin <сток>.bin --patches patches.json \
  --out out.bin --report report.json
```

Статусы: `READY` (план проверен), `EMPTY` (значения уже совпадают со стоком;
строка `CELLS_ALREADY_MATCH`), `REJECTED` (нарушение политики или арифметики),
`WRITTEN` (файл записан). `--json` печатает полный отчёт в stdout. Отчёт JSON содержит SHA-256 до/после, каждый изменённый байт, старые и
новые значения, пересчитанные записи CRC и признак `crc_valid_after`.

## 2. Политика (v1, 18 объектов)

Файл — `MS42/policies/stage_policy.json`. Для каждого объекта заданы `min`,
`max`, максимальная дельта от стока, при необходимости — монотонность и
количество ячеек.

| Объект | Адрес (отн. калибровки) | Сток | Пределы |
| --- | --- | --- | --- |
| `c_vs_max_1` | `0x042F` | 216 км/ч на B20, 255 на остальных | 0..255 |
| `c_vs_max_add` | `0x0430` | 40 (5.0 км/ч) | 0..31.875 км/ч |
| `c_vs_max_hys` | `0x0433` | 3 км/ч | 0..20 |
| `c_n_min_vs_max` | `0x02DD` | 800 об/мин | 0..8160, только по прямому запросу |
| `id_n_max_mt__nvs` | `0x769E` | 6624/6496/6496 или 6624/6528/6528 | 2000..8160, 3 ячейки |
| `id_n_max_max_mt__nvs` | `0x769B` | 6624/6592/6592, 6688/6624/6624 или 6592 | 2000..8160, 3 ячейки |
| `id_n_max_at__nvs` | `0x7689` | 6496 или 6592/6496 | 2000..8160, 3 ячейки |
| `id_n_max_max_at__nvs` | `0x7698` | 6592 или 6656/6592 | 2000..8160, 3 ячейки |
| `id_n_max_cycnr__vs` | `0x76A1` | 13/19/23/26/26, 1/1/20/40/40 и др. | 0..255, 5 ячеек |
| `c_n_max_hys` | `0x02EE` | 0 (B20/B25) или 32 (B28) об/мин | 0..512 |
| `c_n_max_hys_max` | `0x02F0` | 800 или 320 об/мин | 0..1600 |
| `c_n_hys_max_puc` | `0x02C8` | 640/480 об/мин | 0..1600 |
| `c_n_hys_min_puc` | `0x02CA` | 448/128 об/мин | 0..1024 |
| `ip_n_min_puc__tco` | `0x55EA` | по таблице | 0..8160, 6 ячеек |
| `ip_n_min_accin_puc__tco` | `0x55F0` | по таблице | 0..8160, 6 ячеек |
| `ip_iga_puc__n__tco` | `0x73A1` | −13.125..−4.875 °CRK (B20), −12.0..−4.5 (B28) | −23.625..0, 24 ячейки |
| `ip_t_puc_deacc__n__maf_mmv` | `0x35F6` | 0.48..1.7 с | 0..8 с (санитарный предел), 24 ячейки |
| `id_maf_tab` | `0x17A6` | пик 777.9 кг/ч | 0..1023.98 кг/ч, ±30 %, монотонная, 256 ячеек |

Две таблицы намеренно названы не по единицам из XDF: у `ip_iga_puc__n__tco` в
XDF стоит `[°C]`, хотя значения — градусы поворота коленвала (0.375 на шаг при
смещении −23.625), а у `ip_t_puc_deacc__n__maf_mmv` стоит `[mg/strk]`, хотя это
секунды (0.000128 на шаг). Это дефекты подписей в определении, а не ошибка
политики; предел `ip_t_puc_deacc__n__maf_mmv` в 8 с — санитарный: сток лежит в
0.48..1.7 с, а всё, что больше нескольких секунд, не является калибровкой
отсечки.

Поля политики: `min`, `max`, `max_delta_percent`, `max_cells_per_patch`,
`require_monotonic`, `xdf_index` (для заголовков, которые в XDF объявлены
несколько раз) и `note` — обоснование со ссылкой на стоковое значение.

«Сток» различается по вариантам: например, `c_vs_max_1` = 216 на части машин
(в том числе M52TUB20) и 255 на остальных. Политика задаёт границы
(`min`/`max`) и число ячеек, а не одно «правильное» значение: стоковое значение
ядро читает из самого образа при планировании. Максимальная дельта от стока
(`max_delta_percent`) сейчас задана только для кривой MAF (±30 %), чтобы правка
оставалась в пределах «тот же датчик, поправленная кривая».

## 3. Что политика запрещает

* Любые объекты вне allowlist (статус `SYMBOL_NOT_ALLOWED`) — включая
  структурные байты и калибровочные таблицы, для которых нет измеренного
  обоснования.
* Режим «`(MAF Hack 2048kg/h)`»: он требует патча программной части, а не
  правки калибровки, и отклоняется.
* Две записи в одну и ту же ячейку за один проход (`OVERLAPPING_WRITES`).
* Значения, не представимые квантом АЦП/таблицы (`VALUE_NOT_REPRESENTABLE`),
  и слишком грубое округление (`QUANTIZATION_TOO_COARSE`, порог 1 %).
* Выход за пределы покрытия CRC (`OUTSIDE_CRC_COVERAGE`): последний защищённый
  байт калибровки — `0x4F843` (абсолютный). Всё, что выше, лежит вне блока
  калибровки и этой записи не покрывается.

## 4. Контрольные суммы внутри ядра

Перед записью ядро проверяет исходный образ целиком: если сток не сходится по
контрольным суммам, планирование отклоняется (`SOURCE_CRC_INVALID`), потому что
неизвестно, от чего считать дельты. После записи пересчитываются только те
записи, которые затронуты правкой; для правок внутри калибровки это всегда
только `cal`. Затем выполняется повторная проверка, и образ отдаётся лишь при
`crc_valid_after = true`.

## 5. Тесты

```bash
python3 -m unittest discover -s MS42/tests -t .   # 133 теста
```

Среди них: отказ на символ вне политики, отказ на структурный байт, отказ на
неверный тип значения, отказ на две правки одной ячейки, поведение
`CELLS_ALREADY_MATCH`, монотонность кривой MAF, недостающие/лишние ячейки,
повторный пересчёт CRC и побайтовое сравнение с ожидаемым результатом на
реальных стоковых образах.
