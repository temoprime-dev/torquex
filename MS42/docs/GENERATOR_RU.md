# Генератор нарядов MS42: запрос клиента → патч-план

`MS42/tools/generate_patches.py` — слой между заявкой клиента и ядром
патчинга. Заявка описывает **намерения** («снять ограничитель скорости»,
«поднять отсечку до 6700»), а не адреса и байты. Генератор превращает намерения
в конкретные пары «символ + значение», прогоняет результат через настоящее ядро
патчинга (dry-run) и отдаёт файл патча только при статусе `READY`.

Главное правило то же, что в MS41: **значение попадает в план только тогда,
когда его назвал клиент или оно взято из файла, который у нас есть.** Ничего не
«подбирается» по форумам.

## 1. Запуск

```bash
python3 MS42/tools/generate_patches.py \
  --bin MS42/firmware/Siemens_MS42_0110C6_E46_M52TUB20_EU3.bin \
  --request MS42/examples/stage1_request.example.json \
  --out patches.json --report generation.json
```

* `--out` — файл патча для `calibration.py` (пишется только при `READY`);
* `--report` — полный отчёт (намерения, обоснования, требования, план ядра);
* `--json` — печатать отчёт в stdout.

Файл патча — объект с `status` (`READY`/`BLOCKED`), `source`, `patches` и
полями источников. `calibration.py` отказывается работать с файлом, у которого
статус не `READY`: нельзя случайно записать половину наряда.

## 2. Намерения, которые пишут значения

### `vmax` — ограничитель скорости

| Параметр | Смысл |
| --- | --- |
| `value_kmh` | порог мягкого ограничения (`c_vs_max_1`) |
| `hard_add_kmh` | добавка к жёсткой ступени (`c_vs_max_add`, умолчание — сток) |
| `disable: true` + `acknowledge_risk: true` | поднять порог активации `c_n_min_vs_max` до 8160 об/мин, то есть «выключить» ограничитель |

Факты, которые генератор печатает, а не скрывает: сток `c_vs_max_1` = 216 км/ч
на части машин и 255 на остальных; 255 — максимум шкалы, поднимать выше некуда;
жёсткая ступень срабатывает на `c_vs_max_1 + c_vs_max_add` отсечкой бензонасоса.
Понижение порога разрешено, но помечается предупреждением `LIMIT_LOWERED`.

Без `acknowledge_risk` снять ограничитель нельзя: статус `REQUIRES_DATA` с
требованием подтвердить, что клиент понимает риск.

### `rpm_limit` — ограничитель оборотов

| Параметр | Смысл |
| --- | --- |
| `transmission` | обязателен: `manual` или `auto` |
| `soft_rpm` | мягкая отсечка (`id_n_max_mt/at__nvs`), число или до 3 значений по передачам |
| `hard_rpm` | жёсткая отсечка (`id_n_max_max_mt/at__nvs`), иначе остаётся сток |
| `hysteresis_rpm` | `c_n_max_hys` |
| `hysteresis_max_rpm` | `c_n_max_hys_max` |
| `acknowledge_risk` | обязателен при подъёме выше стока |
| `acknowledge_oil_pump` | обязателен при подъёме выше 6750 об/мин (после `acknowledge_risk`) |

Мягкая отсечка не может быть выше жёсткой (`SOFT_ABOVE_HARD`); несостяковка
сообщается раньше, чем запрос подтверждений. Подъём выше стока требует
`acknowledge_risk`: клапанный механизм, масляный насос и штатная защита
рассчитаны на заводской предел — это решение клиента, а не оптимизация
генератора. Выше **6750 об/мин** нужно второе, отдельное подтверждение
`acknowledge_oil_pump` (`HIGH_RPM_OIL_PUMP_ACK_REQUIRED`): таблицы представимы до
8160 об/мин, но штатный насос — известное слабое место, а измерений,
доказывающих безопасный подъём, в репозитории нет. Таблицы «другой» коробки не
трогаются и это явно фиксируется в отчёте (`OTHER_GEARBOX_TABLES_UNTOUCHED`).

### `hardcut` — гистерезис отсечки на сбросе газа

| Параметр | Смысл |
| --- | --- |
| `upper_rpm` | `c_n_hys_max_puc`: порог возврата отсечки |
| `lower_rpm` | `c_n_hys_min_puc`: порог удержания отсечки |

Пересечение порогов (`lower > upper`) отклоняется как `HYSTERESIS_INVERTED`.
Это **не** popcorn: задержка и углы зажигания не меняются.

## 3. Намерения, для которых нужен стенд или логи

Пять видов намерений не пишут ни одного байта: `ignition`, `fueling`, `vanos`,
`maf_curve`, `launch_limiter`. Каждое возвращает статус `REQUIRES_DATA` и
«требования» (`requirements`) с конкретными символами XDF, логами, стендовыми
шагами и воротами. `popcorn` тоже отдаёт требования, но у него есть рабочий
путь: `stages.py --popcorn` пишет хлопки по профилю клиента (см.
`STAGES_RU.md`). Полные требования — в `EVIDENCE_REQUIREMENTS_RU.md`.

Причина одна: сток MS42 работает с узкополосной лямбдой и заводскими таблицами
детонации, а измеренных данных по конкретной машине у нас нет. Любые
«+X градусов» или «+X л.с.» без стенда и логов были бы выдумкой, поэтому
генератор честно отдаёт список того, что нужно измерить.

## 4. Статусы

| Статус | Что значит |
| --- | --- |
| `READY` | все намерения развернулись, ядро приняло план сухим прогоном |
| `EMPTY` | запрос не дал изменений (например, значение уже равно стоку) |
| `REQUIRES_DATA` | намерение ждёт данных, значения не пишутся |
| `BLOCKED` | есть противоречие или отказ (неизвестный тип, мягкая выше жёсткой и т. п.) |

Если хотя бы одно намерение `BLOCKED` — весь наряд `BLOCKED` и файл патча не
отдаётся. Намерения `REQUIRES_DATA` сами по себе блокируют только себя: остаток
наряда остаётся `READY` и явно перечислен в отчёте (колонка «Что не выполнено» в
наряде клиенту).

## 5. Проверка, что генератор не врёт

Тесты (`MS42/tests/test_generate_patches.py`, 27 тестов) проверяют:

* каждый символ, названный в требованиях, существует в XDF MS42 (однажды
  генератор MS41 сослался на несуществующий символ — больше никогда);
* подъём отсечки и снятие ограничителя без `acknowledge_risk` не проходят;
* мягкая выше жёсткой, пересечённый гистерезис и неизвестный тип отклоняются;
* сгенерированный файл патча принимается ядром **как есть**, собирается в BIN и
  результат проходит `analyze_firmware.py`;
* таблицы «другой» коробки в план не попадают.
