# Рабочий маршрут MS45: от заявки клиента до файла и наряда

Документ описывает полный цикл работы по MS45 — ровно так, как требует задание
(`MS45/TASK_RU.md`): **запрос клиента → план патча с обоснованием → готовый файл
→ наряд**. Пример наряда, собранного этим маршрутом, лежит в
`MS45/examples/stage1_naryad.example.md`.

## 1. Что нужно на входе

1. **Чтение ЭБУ** — полный образ 1 МиБ **или** калибровка 116 КиБ.
   * Полное чтение (1 МиБ) принимается, но записывается в нём только область
     `0x40000..0x5CFFF`; остальное обязано остаться байт в байт.
   * Чтение внутренней флеш MPC (448 КиБ) **не принимается**: `MPC_IMAGE_UNSUPPORTED`.
2. **Семейство в идентификаторе**. Полностью поддерживаются `4560BO00S`
   (MS45.0, SW 456), `4570LO00S` (MS45.1, SW 457) и `4560BN00S` (MS45.0, SW 456).
   `4560BM00S` поддерживается только для таймерного пакета `pops`; Vmax и RPM
   возвращают `REQUIRES_DATA`. Остальные целевые семейства → `CAL_VERSION_UNSUPPORTED`
   (адреса между версиями не переносятся).
3. **Обе контрольные суммы обязаны сходиться** в исходном файле: `SOURCE_CRC_INVALID`
   иначе. Это защищает от «уже кем-то правленного» файла.
4. **Заявка клиента** (JSON) — что именно нужно: скорость, отсечка, хлопки,
   подтверждения.

## 2. Проверка исходника

```bash
python3 -m MS45.tools.checksums чтение.bin --explain
```

В отчёте видно: размер, семейство, хранимую и расчётную CRC-32, пару MO3 и её
смещение. Если суммы не сходятся — файл не годится, пока не разобрано, почему
(наши инструменты умеют и восстановить суммы: `--repair`, но для чужого файла
это отдельное решение, а не рутина).

## 3. Сборка

```bash
python3 -m MS45.tools.stages \
    --image чтение.bin \
    --stage stage1 \
    --request заявка.json \
    --out stage1.bin \
    --note-out naryad.md \
    --manifest-out manifest.json
```

Что происходит внутри:

1. Генератор разбирает намерения, проверяет ворота (подтверждения, профиль
   хлопков, наличие железа для Stage 2) и собирает пакеты.
2. Каждый «пишущий» пакет становится списком запросов `{символ: значения}`.
3. Ядро строит план: allowlist, квантование, границы, дельта к стоку, пересечения
   ячеек; при любом нарушении — отказ с кодом.
4. Ядро применяет план: ячейки → пара MO3 → CRC-32 → пост-проверка «изменилось
   только плановое».
5. Пишутся файл, наряд (Markdown по-русски) и манифест (JSON для учёта).

## 4. Что получает клиент

* **Файл** — байты калибровки с пересчитанными суммами.
* **Наряд** — что записано (таблица ячеек: адрес, было, стало, единицы), что
  **не** менялось (области вне калибровки, RSA-подпись, штатные защиты), что
  требует данных, предупреждения и порядок прошивки.
* **Манифест** — тот же результат машинно-читаемо: sha256 файла, ячейки,
  изменённые байты, слова сумм, план целиком.

## 5. Проверка результата перед прошивкой

```bash
python3 -m MS45.tools.checksums stage1.bin --explain   # суммы должны быть ok
```

Дополнительно можно убедиться, что изменилось ровно ожидаемое: в манифесте есть
`changed_cells` и `checksum_words`, а также полный список ячеек с адресами.

## 6. Прошивка (вне нашего инструмента)

1. Сохранить исходное чтение ЭБУ.
2. Прошить **область калибровки** `0x40000..0x5CFFF` (тюнинг-флешер, «tune
   flash»). Программа `0x60000..0xFFFFF` и нижняя область `0x00000..0x3FFFF` не
   записываются — там возможные VIN/ISN/EWS и стартовый код.
3. Проверить, что ЭБУ не сообщает ошибок по контрольным суммам: обе суммы в
   файле уже посчитаны нашим ядром, но если флешер пересчитывает их сам —
   результат обязан совпасть (схема та же).
4. Первый запуск — на месте: холостой ход, отсечка, ограничитель скорости,
   отсутствие ошибок в памяти неисправностей.

**Чего маршрут не делает:** не переподписывает RSA-подпись калибровки (ключ BMW
недоступен), поэтому файл предназначен для путей прошивки, которые не проверяют
подпись. Путь штатного WinKFP/ISTA требует переподписи на стороне, которая это
умеет, и в наряде это сказано прямо.

## 7. Отказы: что увидит клиент

| Код | Причина | Что делать |
| --- | --- | --- |
| `REQUIRES_DATA` | функция не доказана для SW-ID/пакетной роли (например Vmax/RPM для BM00S) | не писать объект; получить версионно привязанные данные, перечисленные в наряде |
| `CAL_VERSION_UNSUPPORTED` | SW-ID не входит в разрешённые семейства (`4560BO00S`, `4570LO00S`, `4560BN00S`, `4560BM00S`) | нужны собственные определения/доказательства; адреса другой версии не переносятся |
| `SOURCE_CRC_INVALID` | исходник не проходит суммы | взять чистое чтение или разобраться, кто и чем правил файл |
| `MPC_IMAGE_UNSUPPORTED` | подсунули внутреннюю флеш 448 КиБ | нужно полное чтение 1 МиБ или калибровка 116 КиБ |
| `POLICY_RANGE_VIOLATION` | значение вне допуска (например отсечка 7500) | обсудить с клиентом выполнимое значение |
| `ACKNOWLEDGE_REQUIRED` | нет подтверждения (катализатор/риск/температура) | получить подтверждение письменно |
| `POPS_PROFILE_FORBIDDEN` | запрошен агрессивный профиль хлопков | не выпускается: только `light`/`medium` |
| `HARDWARE_REQUIRED` | Stage 2 без профиля железа | собрать профиль железа и замеры |
| `NOTHING_TO_DO` | значения уже такие | файл не нужен |

## 8. Воспроизводимость

Все проверки воспроизводимы одной командой:

```bash
python3 -m unittest discover          # весь репозиторий
python3 -m unittest MS45.tests        # только MS45
```

Тесты MS45 заново проверяют по образам: суммы всех 239 калибровок, адреса и
формулы из определений, диапазоны стока, отказы ядра и генератора, а также
cp1251-совместимость консольного вывода (русская Windows).
