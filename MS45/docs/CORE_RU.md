# Ядро патчинга MS45: единственный путь к записи

`MS45/tools/calibration.py` — это **единственное** место, которое меняет байты
образа. Генератор (`stages.py`) не пишет сам: он формирует запросы и передаёт их
ядру. Ядро работает и с калибровкой 116 КиБ, и с полным образом 1 МиБ.

## 1. Порядок работы

```
запрос клиента (JSON)
   ↓  stages.py: пакеты -> список запросов {символ: значения}
plan_changes(image, requests, policy, acknowledgements)
   ↓  проверки входа, allowlist, квантование, границы, дельта, подтверждения
PatchPlan (PLANNED или REJECTED со списком отказов)
   ↓  apply_plan(image, plan)
ячейки -> пара MO3 -> CRC-32 -> пост-проверка «изменилось только плановое»
   ↓
готовый файл + PatchResult (sha256, ячейки, изменённые байты, слова сумм)
```

План всегда строится по конкретному образу: `source_sha256` входит в план, и
`apply_plan` откажется применять план к другому файлу.

## 2. Что проверяется в плане

| Проверка | Код отказа |
| --- | --- |
| размер образа (116 КиБ или 1 МиБ) | `IMAGE_SIZE_UNSUPPORTED` |
| внутренняя флеш MPC (448 КиБ) | `MPC_IMAGE_UNSUPPORTED` |
| семейство поддерживается политикой | `CAL_VERSION_UNSUPPORTED` |
| исходник проходит **обе** свои суммы | `SOURCE_CRC_INVALID` |
| значение в исходнике внутри измеренного стока семейства | `SOURCE_NOT_STOCK` |
| символ есть в allowlist | `SYMBOL_NOT_ALLOWED` |
| символ не «только чтение» | `READ_ONLY` |
| значение в границах допуска | `POLICY_RANGE_VIOLATION` |
| значение выразимо в разрядности | `VALUE_NOT_REPRESENTABLE` |
| ошибка квантования не выше 1 % | `QUANTIZATION_TOO_COARSE` |
| отклонение от стока не выше предела символа | `DELTA_TOO_LARGE` |
| число значений = 1 или = числу ячеек | `CELL_COUNT` |
| символ не запрошен дважды | `DUPLICATE_SYMBOL` |
| ячейки не пересекаются | `OVERLAPPING_WRITES` |
| ячеек не больше 2048 | `TOO_MANY_CELLS` |
| подтверждения на месте (`no-catalyst` и т. п.) | `ACKNOWLEDGEMENT_REQUIRED` |
| план что-то меняет | `NOTHING_TO_DO` |

Отказы **накапливаются** (пользователь видит все причины), но план при любом
отказе получает статус `REJECTED` и применить его нельзя.

Проверка `SOURCE_NOT_STOCK` — это защита от чужой версии: у каждого семейства
политика хранит измеренный сток (минимум/максимум по всем стоковым файлам
семейства, поле `stock`). Правка ячейки, текущее значение которой лежит вне этого
диапазона, отвергается: значит, в файле уже кто-то правил или это другая версия,
где по этому адресу лежит что-то ещё. Мы работаем только от стоковой калибровки —
именно поэтому адресам политики можно доверять.

## 3. Что именно пишется

1. Ячейки плана (big-endian, как в стоке MS45).
2. Пара MO3 по смещению **своего** семейства (только если область `0x240..0x7C8`
   затронута).
3. CRC-32 по `0x100` — всегда, и **после** записи пары MO3 (пара лежит внутри
   области CRC; порядок обязателен, иначе CRC окажется неверной — это ловится
   тестом).

Ничего больше. Пост-проверка сравнивает исходный и готовый образ и требует,
чтобы все различия лежали в множестве «ячейки плана + байты сумм». Иначе —
отказ `OUTSIDE_PLAN_CHANGE`: это защита от ошибки в самом ядре.

## 4. Границы: чего ядро не сделает никогда

* Не запишет байт вне `0x40000..0x5CFFF`. В полном образе 1 МиБ это проверяется
  отдельно тестом: после правки файл обязан совпадать с исходным **байт в байт**
  везде, кроме области калибровки.
* Не тронет `0x174..0x1B3` (RSA-подпись) и заголовок `0x104..0x16F`
  (дескрипторы областей): они не покрыты суммами, и их изменение бессмысленно.
* Не станет «поправлять» суммы вне области калибровки: их там для нашей правки
  нет. Нижняя область `0x00000..0x3FFFF` имеет свой CRC-дескриптор на `0x1F800`
  (область `0x00000..0x1EFFF`), но нам туда нельзя, поэтому и пересчитывать там
  нечего.

## 5. Квантование

Числа клиента — инженерные; ядро переводит их в сырые коды по формуле из XDF,
округляет «половина вверх» и считает ошибку в процентах. Если ошибка больше
предела политики (по умолчанию 1 %), план отвергается: значит, шаг слишком
грубый и клиент получит не то, что просил. Ошибка по каждой ячейке пишется в
план — её видно и в JSON, и в наряде.

## 6. CLI

```bash
# план без записи
python3 -m MS45.tools.calibration --image сток.bin --set c_vs_max=255 --dry-run

# запись с пересчётом сумм
python3 -m MS45.tools.calibration --image сток.bin \
    --set c_vs_max=255 --set id_n_max_mt=6800 --set id_n_max_h_mt=6800 \
    --out stage1.bin --json-out plan.json

# хлопки (обязательно подтверждение отсутствия катализатора)
python3 -m MS45.tools.calibration --image сток.bin \
    --set c_t_min_pu=0.5 --set c_t_min_pu_vs=0.5 --set c_t_min_pu_rng_l=0.5 \
    --acknowledge no-catalyst --out stage1_pop.bin
```

## 7. Тесты

`MS45/tests/test_calibration.py` — 36 проверок: каждый код отказа, запись одной
ячейки и таблицы целиком, `None` как «оставить как есть», полный образ 1 МиБ
(байтовое равенство вне калибровки), пост-проверка, повторное применение
(`NOTHING_TO_DO`), оба семейства, CLI и его коды возврата.
