# Stage 1 / Stage 2 для MS45: что выпускается и что нет

Генератор — `MS45/tools/stages.py`. Заявка клиента (JSON) превращается в набор
пакетов; каждый пакет либо пишет значения через ядро, либо честно отвечает
`REQUIRES_DATA` со списком того, что нужно измерить. Догадок в файле не бывает.

## 1. Заявка клиента

```json
{
  "stage": "stage1",
  "customer": "E46 330i, M54B30, MT",
  "notes": "катализатор удалён",
  "no_catalyst": true,
  "acknowledge_temperature": true,
  "intents": [
    {"kind": "vmax", "value": 255},
    {"kind": "rev_limit", "value": 6800, "transmission": "mt", "acknowledge_risk": true},
    {"kind": "pops", "delay_s": 0.5, "profile": "light"}
  ]
}
```

Примеры лежат в `MS45/examples/`:
`stage1_request.example.json`, `stage1_request_empty.example.json` (заведомо
негодная заявка — без подтверждений), `stage1_request_launch_control.example.json`,
`stage2_request_intake.example.json`.

### Намерения

| `kind` | Параметры | Пакет | Что делает |
| --- | --- | --- | --- |
| `vmax` | `value` (км/ч) | `limits` | `c_vs_max` |
| `rev_limit` | `value` (rpm), `transmission` = `mt`/`at`/`amt`, `acknowledge_risk`, `acknowledge_damper` | `limits` | пара `id_n_max_*` + `id_n_max_h_*` (все 9 ячеек) |
| `pops` | `delay_s` (0.05..1.5), `profile` (`light`/`medium`) | `pops` | три задержки ПХХ |
| `pops_intensity` | — | `pops_intensity` | **не выпускается** → `REQUIRES_DATA` |
| `cat_delete` | заявка с `no_catalyst: true` | `cat_delete` | слой «без катализатора»: флаги `c_conf_cat`, подогрев/диагностика заднего зонда (см. §6в) |
| `sap_delete` | заявка с `no_catalyst: true` | `sap_delete` | слой «без катализатора»: задержки продувки в 0, диагностика СВП выключена (см. §6в) |
| `idle_speed` | — | `idle_speed` | **не выпускается** → `REQUIRES_DATA` |
| `disa` | — | `disa` | **не выпускается** → `REQUIRES_DATA` |
| `injectors` | — | `injectors` | **не выпускается** → `REQUIRES_DATA` |
| `e85` | — | `e85` | **не выпускается** → `REQUIRES_DATA` |
| `launch_control` | — | `launch_control` | **не выпускается** → `REQUIRES_DATA` (калибровочного пути нет, патч кода запрещён) |
| `octane` | `fuel` = `ron98`/`ron95`/`ron91` (либо поле заявки `octane`) | — (ворота) | профиль топлива варианта 1: добавку зажигания получает только RON98; RON95/RON91 — стоковые карты (`OCTANE_PROFILE_NO_ADDITION` при попытке добавки) |
| `disa_off` | — | `disa_off` | **не выпускается** → `REQUIRES_DATA`: нужны состояние механики, причина и логи наполнения |
| `isa_off` | — | `isa_off` | **не выпускается** → `REQUIRES_DATA`: нужно подтверждение (клапан снят, канал ХХ заглушен) и лог устойчивости ХХ |
| `fan_thermostat` | — | `fan_thermostat` | **не выпускается** → `REQUIRES_DATA`: нужен трековый сценарий и лог температур |
| `ignition` | `delta_deg` (0..3), `evidence` | `ignition` | добавка к карте `ip_iga_bas_ron_98__n__maf` (см. §6а) |
| `fuel` | `ti_fl_enrich_lambda` (≤0.03), `evidence` | `fuel` | обогащение `ip_lamb_fl__n` (только 4570LO00S, см. §6а) |
| `vanos` | `shift_in_deg`/`shift_ex_deg` (±5), `evidence` | `vanos` | прогретые карты фаз частичной нагрузки (см. §6а) |
| `stage2` | требуется блок `hardware` | `hardware` | **не выпускается** без стенда → `REQUIRES_DATA` |

Нереализованные намерения не отказ заявке: остальные пакеты собираются, а в наряде
по каждому появляется причина и список того, что нужно измерить (см. §6).
Пакеты `limits` и `pops` собираются на **всех десяти** семействах: у BO00S/LO00S
адреса даёт XDF, у BN00S — проверенная XML-карта, у остальных семи
(`4560BM00S`, `4560BL00S`, `4560BL30S`, `4570LL00S`, `4570LL30S`, `4570LM00S`,
`4570LN00S`) — структурные отпечатки по стокам своей семьи
(`FAMILY_CALIBRATION_EVIDENCE_RU.md` §2–3, тест `test_family_stock_proof.py`).
Карты (зажигание, топливо, ВАНос) и диагностика привода в этих семи семействах
остаются `REQUIRES_DATA`.

## 2. Ворота продукта

| Ворота | Условие | Что нужно |
| --- | --- | --- |
| выше стока | `rev_limit` больше стокового значения этой прошивки | `acknowledge_risk: true` у намерения |
| демпфер | `rev_limit` > 6900 rpm | `acknowledge_damper: true` (M54B30: ms4x.net про гармонику) |
| хлопки | запрошен `pops` | `no_catalyst: true` в заявке (подтверждение клиента) и `acknowledge_temperature: true` |
| профиль хлопков | `aggressive`/`extreme`/… | отказ `POPS_PROFILE_FORBIDDEN`: выпускаются только `light`/`medium` |
| Stage 2 | нет блока `hardware` | отказ `HARDWARE_REQUIRED` целиком |
| правовая справка | запрошены `pops`, `cat_delete`, `sap_delete` | `acknowledge_legality: true` (в заявке или в намерении), иначе отказ `ACKNOWLEDGE_LEGALITY_REQUIRED` |
| профиль топлива | `octane` = RON95/RON91 | добавка зажигания не пишется: отказ `OCTANE_PROFILE_NO_ADDITION`; конфликт поля заявки и намерения — `OCTANE_PROFILE_CONFLICT` |
| мощность | всегда | ни одной цифры прироста: без стенда обещаний нет |

Подтверждения клиента попадают в пакет `pops` ещё и через ядро
(`--acknowledge no-catalyst`), так что обойти их нельзя ни через генератор, ни
через ядро.

## 3. Статусы сборки

| Статус | Когда | Файл |
| --- | --- | --- |
| `BUILT` | есть записанные пакеты, план принят | выпускается, пишется наряд |
| `REQUIRES_DATA` | ничего не записано, но есть пакеты «ждут данных» | файла нет; наряд объясняет, что нужно |
| `REJECTED` | есть отказ (нет подтверждений, значение вне допуска, чужая версия и т. п.) | файла нет; наряд всё равно печатается с причинами |

Код возврата CLI: `0` — файл выпущен (или `--dry-run` без отказов), `2` — отказ
или «нужны данные». Наряд (`--note-out`) пишется и в отказных случаях: он и есть
объяснение клиенту.

## 4. Что такое «Stage 1» и «Stage 2» здесь

**Stage 1** — то, что доказуемо на стоковом железе из калибровки: ограничитель
скорости, отсечка по оборотам, задержка ПХХ (хлопки). Никаких углов зажигания,
смеси и лимитов момента — для них нужен стенд (см. `ANALYSIS_WEB_RU.md`, §7).

**Stage 2** — привязан к конкретному железу и **не собирается** без профиля
железа и замеров: генератор выдаёт список требований (артикулы впуска/ДМРВ/
форсунок/наддува, логи или стендовые замеры нагрузки и смеси, подтверждение по
детонации и температуре выпуска). Когда данные появятся, они добавляются в
политику как отдельные символы со своими границами — но не раньше.

**Launch control** в MS45 не выпускается: в MS43 эта функция делается патчем
кода, а правка программы запрещена заданием (область правок — только
калибровка). Это `REQUIRES_DATA` с отдельным решением владельца.

## 5. Наряд

`--note-out` пишет Markdown-наряд по-русски:

* шапка: клиент, дата, статус, sha256 исходника, семейство, версия политики;
* **Что записано** — по пакетам и таблица ячеек (адрес, было, стало, единицы) +
  изменённые слова контрольных сумм;
* **Замечания ядра и продукта** — таблица находок (отказ / внимание / к сведению)
  с кодами: наряд по отказной заявке объясняет клиенту причину, а не только
  возвращает код 2;
* **Что НЕ менялось** — области вне калибровки, RSA-подпись, штатные защиты;
* **Что требует данных** — что именно нужно измерить;
* **Предупреждения** — мощность не обещается, подпись и путь прошивки, «только
  эта калибровка», хлопки без катализатора, демпфер;
* **профиль топлива** — в шапке (RON98/RON95/RON91) с объяснением, что даёт
  профиль;
* **Правовая справка** — RU + EN, со ссылками (Регламент (ЕС) 715/2007
  ст. 3 п. 10 и ст. 5 п. 2, Правила ЕЭК ООН № 83, Clean Air Act § 203(a)(3),
  40 CFR § 1068.101(b)) и датой проверки; печатается, когда в заявке есть
  хлопки/диагностика;
* **Откат на сток** — sha256 стока, порядок возврата и команда проверки
  `--verify-manifest`;
* **Порядок прошивки** — сохранить сток, прошить область `0x40000..0x5CFFF`,
  проверить отсутствие ошибок по суммам, первый запуск с контролем.

Текст наряда проверяется тестом на отсутствие обещаний прироста мощности
(регулярные выражения на «+N л.с.», «N hp», «прирост N»).

## 6. Каталог «что требует данных»

Единственный источник правды — `REQUIRES_DATA_CATALOG` в `MS45/tools/stages.py`:
на каждый нереализованный пакет там лежит `why` (почему не выпускаем) и `needs`
(что именно нужно измерить). Пакет получает статус `requires_data`, в находках
появляется `info` с кодом `<ПАКЕТ>_REQUIRES_DATA`, а в манифесте — блок
`requires_data` с тем же списком. Ни одна из этих функций не выпускается «по
умолчанию» и не выпускается вообще, пока не появится доказательство.

| Пакет | Почему не выпускается |
| --- | --- |
| `vmax` | для BM00S не доказаны собственный адрес и масштаб ограничителя скорости; нельзя переносить другие версии |
| `rev_limit` | у BM00S 6×9-кандидат не имеет однозначно подтверждённых осей/назначения и пар по трансмиссиям |
| `pops` | если семейство не имеет своей доказанной группы таймеров, нужны адреса/скейл по всем его стокам; BM00S разрешён только отдельно подтверждённый таймерный блок |
| `pops_intensity` | углы зажигания на частичных нагрузках влияют на всю область и мониторинг момента; «на глаз» — выдумывание |
| `cat_delete` | отключение диагностики катализатора меняет лампу и аварийные режимы — только осознанным решением владельца |
| `sap_delete` | отключение продувки даёт ошибки по вторичному воздуху и влияет на прогрев катализатора |
| `idle_speed` | таблицы холостого хода правятся только вместе с проверкой устойчивости и адаптаций |
| `disa` | пороги заслонки впуска привязаны к конкретному коллектору, нужны логи наполнения |
| `injectors` | масштабирование форсунок требует их точной производительности и логов коррекций |
| `e85` | состав смеси и пусковые обогащения без датчика состава и замеров опасны для двигателя |
| `launch_control` | калибровочного пути в MS45 нет (в MS43 это патч кода, а правка программы запрещена) |
| `hardware` (Stage 2) | момент/впуск/форсунки под железо — без профиля железа и стенда это выдумывание |

## 6а. Пакеты «зажигание / топливо / ВАНос» (задание 3)

Ворота и форматы логов — единые с MS43: человекочитаемый документ
`docs/PACKS_LOG_REQUIREMENTS_RU.md`, машиночитаемые пороги —
`docs/pack_log_requirements.json` (код сверяет каждое число доказательства с
порогом; булево «всё хорошо» доказательством не считается).

* **Зажигание** — только карта `ip_iga_bas_ron_98__n__maf`: без лога ≤ +1.5°,
  с логом детонации ≤ +3.0°; угол не убавляется; карта не пишется выше допуска
  политики семейства (сток +3.0°). Карта RON91, fallback-карта и защита по
  детонации (`ip_iga_bas_max_knk__n__maf`) — только чтение. Потолка
  `ip_iga_optm_tco_2` в MS45 нет (в A2L аналога не найдено), поэтому добавка
  пишется **по форме нагрузки** (задание 3 ревью; обоснование и источники —
  `docs/PACKS_WEB_ANALYSIS_RU.md` §8): 0° при нагрузке ≤ 200 мг/такт (ХХ,
  ПХХ, лёгкий круиз), линейный рост до 600 мг/такт, полная добавка с
  600 мг/такт (полная нагрузка). Ось нагрузки читается из самой калибровки
  (общая ось карт `__n__maf`, 16 точек); если ось не найдена — пакет не
  выпускается (`IGNITION_SHAPE_AXIS_NOT_FOUND`). В наряде видно «запрошено /
  записано» с формой.
* **Топливо** — обогащение `ip_lamb_fl__n` (ячейки — сама лямбда) только с
  логом широкой лямбды: сдвиг ≤ 0.03, не ниже пола 0.82 и не ниже ворот
  диагностики богатой смеси `c_lamb_min_ls_act_test_afr` (0.8207 во всех стоках
  4570LO00S); сток богаче не трогается, обеднение запрещено. На 4560BO00S и
  4560BN00S роль не доказана → честное `REQUIRES_DATA`.
* **ВАНос** — только прогретые карты частичной нагрузки
  (`ip_cam_sp_2_in/ex_pl__n__maf_ivvt`), сдвиг ≤ ±5° от стока, прижат к сетке
  0.375° (запрошенные 2° превращаются в 1.875°), всегда по логу фаз. Холодные
  карты и карты полной нагрузки — только чтение.
* **4560BN00S** — адреса карт зажигания и фаз в проверенной карте семейства не
  доказаны (в определениях только человекочитаемые имена), поэтому все три
  пакета отвечают `REQUIRES_DATA`: default-deny, догадок нет.

Доказательство прикладывается к намерению полем `evidence`: либо словарь прямо
в заявке, либо путь к JSON-файлу. Задание 1 ревью: доказательство принимает
только то, что выдал анализатор `tools/pack_log_analyzer.py` (внутри —
`source_sha256` лога и версия анализатора; ворота сверяют результат пересчётом
из исходного CSV). Ручной `pack_log`-JSON отклоняется кодом
`EVIDENCE_MANUAL_JSON`; подробнее — `docs/PACKS_LOG_REQUIREMENTS_RU.md` §7.1.

## 6б. Три варианта поставки (`variant` в заявке)

Поле `variant: "v1" | "v2" | "v3"` собирает заявку в один из продуктовых
вариантов (уточнённые определения — `docs/PACKS_WEB_ANALYSIS_RU.md` §6;
окончательный состав утверждает пользователь). Без поля — свободная сборка.
Намерение вне состава варианта — отказ `VARIANT_SCOPE_VIOLATION`.

| Вариант | Состав | Особые ворота |
| --- | --- | --- |
| `v1` | «Stage 1 базовый» (docs/TASK_VARIANT1_RU.md §1): `ignition` ≤ +1.5°, `octane`, `vmax`, `rev_limit`, `pops`, `cat_delete`, `sap_delete`, `idle_speed`, `disa`, `disa_off`, `isa_off`, `fan_thermostat` | топливо по логу на этом варианте не пишется (с варианта 2); хлопки/диагностика — `no_catalyst` + `acknowledge_legality`; `launch_control` остаётся недоступным |
| `v2` | v1 + `fuel` (по логу), `vanos` (по логу), `vmax`, `rev_limit` | повышение оборотов требует `acknowledge_oil_pump: true` (плюс существующие `acknowledge_risk`/`acknowledge_damper`) |
| `v3` | v2 + `pops`, `cat_delete`, `sap_delete` | обязательное `no_catalyst: true`, предупреждение о законности и план проверки (`V3_LEGALITY_WARNING`); хлопки — по существующим воротам |

На 4560BN00S варианты собирают только то, что разрешает политика семейства
(карты зажигания и фаз там не доказаны — честное `REQUIRES_DATA`).
Примеры: `examples/stage1_variant_v1/v2/v3.example.json`.

## 6в. Слой «без катализатора»: `cat_delete` и `sap_delete`

Только при `no_catalyst: true` в заявке (плюс подтверждение «no-catalyst»
у каждого символа в политике) и только по проверенным флагам (мс4х-вики,
«Cat Delete»); значения проверены по всем стокам семейств:

* `cat_delete` — `c_conf_cat` → 0 (сток 1/2 у 4560BO00S, 2 у 4570LO00S),
  `lc_lsh_down_1/2` → 0 (подогрев заднего зонда), `lc_inh_ls_down_man_deac`
  → 1 (диагностика заднего зонда выключена);
* `sap_delete` — `ip_t_sa_off_0` (8 задержек) → 0, `lc_inh_sa_man_deac` → 1;
  `lc_sa_swi_acq` → 0 (у 4570LO00S в стоке 1).

Намеренно **не трогается**: `c_obd_state_2` (битовая маска, роль бита не
доказана на стоках), `lc_ad_clr_var` (управляется диагностикой/владельцем),
`lc_ls_cat_diag_cdn_man_act` (условие готовности — отдельная процедура).
На 4560BN00S оба слоя — честное `REQUIRES_DATA` (адреса флагов не доказаны).
В наряд добавляется предупреждение о законности (`*_LEGALITY_WARNING`).

## 7. Проверка выпущенного файла по манифесту

Режим `--verify-manifest` — часть отката на сток: им проверяют и выпущенный
файл, и возвращённый сток (sha256 в манифесте — это sha256 исходного образа).

`--manifest-out` — это паспорт работы: исходник, план, ячейки, суммы, находки.
По нему можно проверить **любой** файл, не доверяя тому, кто его пересылал:

```bash
python3 -m MS45.tools.stages --verify-manifest manifest.json --note-out proverka.md
```

Файл берётся из `--image`, а если он не указан — по имени `result_name` из
манифеста (рядом с манифестом). Что проверяется:

| Проверка | Смысл |
| --- | --- |
| `manifest_version` | схема манифеста нам известна (сейчас 1) |
| `status` | в манифесте действительно выпущенный файл |
| `image_size`, `sha256` | это тот самый файл (байт в байт) |
| `checksums` | CRC-32 и MO3 в файле сходятся |
| `family` / `switch` | семейство совпадает; переключатель MO3 не выключен (не `0xA5`) |
| `checksum_words` | слова сумм совпадают с записанными в манифесте |
| `planned_cells` | в каждой ячейке плана лежит ровно то, что планировалось |
| `changed_bytes` | число изменённых байт не меньше заявленного |
| `outside_plan_changes` | изменений вне плана нет (стоковый исходник ищется по `source_sha256` в `firmware/`, `firmware_spdaten/cal/`, `firmware_dumps/`, можно задать `--source-dir`) |
| `cal_region_only` | все изменения — внутри `0x40000..0x5CFFF` |

Итог: `VERIFIED` (всё сошлось), `FAILED` (что-то не сошлось — прошивать нельзя,
код возврата 2) или `NOT_BUILT` (стадия файла не выпускала). Если стоковый
исходник не найден локально, проверка «ничего лишнего» пропускается честной
пометкой — суммы и ячейки проверяются в любом случае.

## 8. Команды

```bash
# Stage 1 из примера заявки, без записи
python3 -m MS45.tools.stages --image сток.bin --stage stage1 \
    --request MS45/examples/stage1_request.example.json --dry-run

# выпуск файла и наряда
python3 -m MS45.tools.stages --image сток.bin --stage stage1 \
    --request MS45/examples/stage1_request.example.json \
    --out stage1.bin --note-out naryad.md --manifest-out manifest.json

# проверка выпущенного файла: суммы и разбор
python3 -m MS45.tools.checksums stage1.bin --explain

# проверка файла по манифесту (паспорту работы)
python3 -m MS45.tools.stages --verify-manifest manifest.json --note-out proverka.md
```

Любой инструмент MS45 запускается и как модуль (`python3 -m MS45.tools.stages`), и
как скрипт (`python3 MS45/tools/stages.py`) — оба способа проверяются тестами
(`test_cli_console.py::ScriptRunTests`), в том числе в условиях русской Windows.
