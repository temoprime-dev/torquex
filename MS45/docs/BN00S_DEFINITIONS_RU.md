# 4560BN00S (E60, SW 456): как получены адреса и почему им можно верить

Третье поддержанное семейство появилось не «по аналогии», а по проверяемой цепочке
доказательств. Ниже — каждый шаг с командой, которой его можно повторить.

## 1. Почему именно BN00S

* в репозитории **38 стоковых калибровок** `4560BN00S` из SP-Daten (E60, 2004);
* это единственное семейство, для которого есть **реальное чтение ЭБУ** —
  `firmware_dumps/MS45.0_0044560BN_fullread_ORI.bin` (1 МиБ, SW `0FS0N`).

Отдельная находка: область калибровки реального дампа **байт в байт совпадает**
с SP-Daten-файлом `MS45.0_0044560BN00S0FS0N_P7574503_cal_116K.bin`
(SHA256). То есть опубликованные стоковые файлы — не «примерно то же», а ровно
то, что читается из машины. Это же подтверждает, что наше «стоковое» основание
для границ политики взято из настоящих данных.

## 2. Источник адресов и его проверка на уже доказанном семействе

Своего XDF для BN00S нет. Адреса взяты из XML-определений сообщества
(`definitions/MS45 ECU Definitions.xml`, авторство pazi88/ba114/zarboz и др.),
где в одном файле лежат определения для 17 ROM, включая `4560BN00`.

**Шаг проверки источника.** В том же файле есть ROM `4560BO00` — семейство, для
которого адреса уже доказаны независимо (XDF + стоковые значения). Сверяем:

| роль | адрес в XML (`4560BO00`) | адрес в политике (XDF) |
| --- | --- | --- |
| ограничитель скорости | `0x18DC` | `0x18DC` |
| отсечка MT / «increased» | `0x60A2` / `0x6090` | `0x60A2` / `0x6090` |
| отсечка AT / «increased» | `0x605A` / `0x607E` | `0x605A` / `0x607E` |
| отсечка AMT / «increased» | `0x6048` / `0x606C` | `0x6048` / `0x606C` |
| порог overrevving | `0x5AE2` | `0x5AE2` |
| задержки ПХХ (3 роли) | `0x5CAA`, `0x5CAE`, `0x5CB0` | те же |
| сброс обученных вариантов | `0x4A06` | `0x4A06` |

Совпадение по **всем** ролям — источник, из которого мы берём адреса для BN00S,
на проверенном семействе не ошибается ни в одном адресе.
Тест: `MS45/tests/test_bn00s.py::TestSourceProvenance`.

## 3. Проверка BN00S по данным

1. **Упаковка без дыр и пересечений.** Шесть таблиц отсечек идут подряд:
   `0x5FDC`, `0x5FEE`, `0x6000`, `0x6012`, `0x6024`, `0x6036`, каждая
   ровно 18 байт (9 значений по 2 байта). Шаг между таблицами равен длине
   таблицы — то есть это действительно шесть таблиц по 9 значений, а не
   случайные байты.
2. **Осмысленные значения во всех 39 файлах** (38 калибровок + реальный дамп):

   | роль | адрес | значения в стоке |
   | --- | --- | --- |
   | ограничитель скорости | `0x18D4` (8 бит) | 235 и 254 км/ч |
   | отсечка MT / increased | `0x6036` / `0x6024` | 6480 и 6520 rpm (9 передач) |
   | отсечка AT / increased | `0x5FEE` / `0x6012` | 6480 и 6520/6620 rpm |
   | отсечка AMT / increased | `0x5FDC` / `0x6000` | 6480 и 6520 rpm |
   | порог overrevving | `0x5A7C` | **7200 rpm во всех 39 файлах** |
   | задержка ПХХ (3 роли) | `0x5C42`, `0x5C48`, `0x5C46` | 0…0.24 / 0.18…0.46 / 0…1.20 с |
   | задержка после MSR | `0x5C44` | **1.00 с во всех 39 файлах** |
   | сброс обученных вариантов | `0x49BE` | 0 во всех файлах |

3. **Внутренние соотношения** держатся в каждом файле: «increased» не ниже
   обычной отсечки по каждой передаче; порог overrevving (7200) выше любой
   отсечки; задержка после MSR — константа, как и у BO/LO.
4. **Реальное чтение машины** даёт то же самое, причём с осмысленной деталью:
   у АКПП отсечка различается по передачам — `6520, 6620, 6620, …`.

Тесты: `MS45/tests/test_bn00s.py::TestStockData`.

## 4. Формулы (масштабы)

XML для BN00 раздел масштабов не заполняет, поэтому формулы определены по данным:

* `c_vs_max` — 1:1, км/ч (значения 235/254 — заводские ограничители E60);
* `id_n_max*` — 1:1, rpm (значения 6480…6660; иные множители дали бы абсурд);
* задержки ПХХ — 0.01 × X секунд. При любой другой трактовке значения 10…120
  означали бы 10…120 секунд задержки отсечки ПХХ, что физически бессмысленно
  (у BO/LO на этих же ролях стоит ровно 0.01 × X).

## 5. Чего мы намеренно НЕ утверждаем

* **Переключатель `val_mo3_swi_cal_cks` для BN не определён.** У BO/LO его адрес
  подтверждён первоисточником и структурой: байт стоит сразу за маркером
  `07 0e 1b 46 52 64 82 96` в дескрипторе MO3. У BN структура дескриптора
  отличается (между маркером и парой MO3 на 8 байт больше), поэтому «пара минус
  0x1D» и «сразу за маркером» дают разные адреса. Оба кандидата равны нулю во
  всех 39 файлах — на проверку суммы это не влияет (она выполняется пересчётом),
  и в политику BN переключатель не внесён. В отчёте `checksums` такие семейства
  помечаются `switch_verified = false`.
* Адреса **не переносились** между семействами: у BN своя карта, у BO/LO — своя.
* Остальные шесть целевых семейств (`BL00S`, `BL30S`, `LL00S`, `LL30S`,
  `LM00S`, `LN00S`) пока отвергаются `CAL_VERSION_UNSUPPORTED`: в XML для них
  размечено от 6 до 18 таблиц и **ни одной** из ролей этого определения (у
  `4570LG23` есть только ограничитель скорости). `BM00S` рассматривается
  отдельно: доказаны только задержки ПХХ, см. `FAMILY_CALIBRATION_EVIDENCE_RU.md`;
  прочие объекты не разрешены.

## 6. Сквозная проверка

```bash
# сборка Stage 1 для E60
python3 -m MS45.tools.stages --image MS45/firmware_spdaten/cal/MS45.0_0044560BN00S0FS0N_P7574503_cal_116K.bin \
    --stage stage1 --request MS45/examples/stage1_request_bn00s.example.json \
    --out stage1_bn.bin --note-out naryad_bn.md

# проверка сумм выпущенного файла
python3 -m MS45.tools.checksums stage1_bn.bin --explain

# тесты семейства
python3 -m unittest MS45.tests.test_bn00s
```

Полный образ 1 МиБ проверяется тестом `TestCoreOnBn.test_full_image_untouched_outside_calibration`:
после правки файл совпадает с исходным **везде**, кроме области `0x40000..0x5CFFF`.
