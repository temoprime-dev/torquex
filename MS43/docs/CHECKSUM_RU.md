# Контрольные суммы MS43: схема, доказательство, грабли

Статус: **подтверждено** на всём корпусе (47 из 51 образа сходятся полностью,
4 расхождения разобраны и документированы ниже).
Инструмент: `MS43/tools/checksum.py`, отчёт: `MS43/checksums/CRC_VERIFY_RU.md`,
тесты: `MS43/tests/test_checksum.py`.

Схему MS42 (`MS42/tools/checksum.py`) в MS43 **не переносили**: у MS43 другой
набор записей, другие адреса и другие начальные значения.

## 1. Алгоритм

CRC-16/ARC: полином 0x8005, отражённая форма 0xA001 (сдвиг вправо), xor-out 0,
вход не отражается, начальное значение своё у каждой записи. Проверочное
значение для `123456789` — `0xBB3D`.

Запись описывает сама себя:

```
u16 crc   (LE)  -- хранимая сумма
u16 count (LE)  -- число сегментов, 1..16
count * (u32 start, u32 end)  -- обе границы включительно
```

CRC считается по конкатенации сегментов в объявленном порядке. Таблицу
сегментов инструмент читает из образа, а не предполагает: битая таблица —
это отказ, а не «тихая» переинтерпретация.

## 2. Где лежат записи

Полный образ 512 КиБ:

| запись | смещение | адресация сегментов |
| --- | --- | --- |
| boot | 0x03C24 | смещения файла (сток: 0x00000..0x0308D) |
| prog | 0x6FDE0 | **адреса памяти**: файл = адрес − 0x80000 |
| cal  | 0x73FE0 | смещения файла (0x70000..0x72FFF, 0x74000..0x7EE17) |

Чтение калибровки 64 КиБ (24 файла в `MS43/firmware_archive/`): только запись
cal, но по смещению `0x3FE0`, и адреса её сегментов — тоже адреса памяти
калибровки: файл = адрес − 0x70000. Записей boot/prog в таком чтении нет.
Это согласуется с XDF: объект `cal_cks` имеет `mmedaddress 0x3FE0`, то есть
для 512K-образа → 0x73FE0.

Сегментов всегда 2 у cal и 1..6 у prog; больше 16 не встречается.

## 3. Начальные значения (init) — не константы

Прошивка читает init как ASCII-пару символов из строк идентификации образа,
младшим байтом вперёд (LE16):

| запись | источник | значение в стоке |
| --- | --- | --- |
| boot | LE16 @ 0x3FE6, в стоке там `--` | 0x2D2D |
| prog | LE16 @ 0x6FFB6, поле кода прошивки в записи ZIF @ 0x6FFB2 | `00` → 0x3030, `10` → 0x3031, `30` → 0x3033 |
| cal | LE16 из двух последних цифр кода версии `4300xx` в ID калибровки (0x7000C для 512K, 0x0000C для 64K) | см. таблицу |

Сам код версии (`4300xx`, ASCII по `0x70008` для 512K и `0x8` для 64K) читает
`checksum.read_cal_version()` — на нём же стоит защита по версии в ядре
патчинга (`CALIBRATION_RU.md` §5a).

Init калибровки по версиям (проверен на всех 64K-чтениях и на всех 512K-образах):

| версия | последние цифры | init |
| --- | --- | --- |
| 430037 | `37` | 0x3733 |
| 430055 | `55` | 0x3535 |
| 430056 | `56` | 0x3635 |
| 430064 | `64` | 0x3436 |
| 430066 | `66` | 0x3636 |
| 430069 | `69` | 0x3936 |

> **Уточнение к `v-arapidis/openremap-core`.** Там для калибровки указан
> `BE16 @ 0x6FFBF`. Для 430069 это даёт 0x3936 — то же значение, но только
> потому, что байты `...6965...` образуют палиндром. На 430037/0055/0056/0064/0066
> правило BE16 @ 0x6FFBF даёт **неверный** init (например 0x3736 вместо
> 0x3733), и суммы не сходятся. Правило LE16 из цифр версии верно на всех
> шести версиях.

Грабли: **нельзя хардкодить 0x3030 для prog**. В архиве есть образы с кодом
прошивки `10` (E46 330i C155G50G, E46 330i b137954g, E53 c356750f) и `30`
(E39 530i b137j54g) — их prog-сумма сходится только со своим init.

## 4. Суммы `_mon` — только runtime (unverified)

В образах есть ещё две суммы:

* `prog_mon` @ 0x6FDAE (u32 LE) — например 0xB3DAAD17 в стоке 430069;
* `cal_mon`  @ 0x72FFC (u32 LE; в 64K-чтении 0x2FFC, в XDF это два 16-битных
  поля `cal_mon_cks_1` @ 0x2FFC и `cal_mon_cks_2` @ 0x2FFE).

Это аддитивные суммы (`lc_swi_*`), которые прошивка сверяет **во время
работы** через XRAM; статически из дампа они не воспроизводятся. Проверено и
закрыто:

* суммы сегментов boot/prog/cal (u8/u16LE/u32LE/i16LE) не равны ни 0xB3DAAD17,
  ни 0xA61EB8D5;
* дифференциальная сверка 11 регионов × 6 разновидностей сумм на 18 образах
  430069 не дала ни одного согласованного региона;
* сумма 4 диапазонов из таблицы @ 0x6FDBE (см. ниже) в любом кодировании
  тоже не совпадает: u32LE = 0xC0185FD5, u16LE = 0x0EA418AE и т.д.

Поэтому в инструменте эти суммы только **показываются** (статус
`unverified`) и никогда не пересчитываются. Так же поступает openremap
(«cal monitor sum @ 0x72FFC: runtime check (not verifiable from a static
dump)»).

Для справки, таблица @ 0x6FDBE (8 × u32 LE): `0xD0000, 0xD3BF8, 0xEE876,
0xEE878, 0x712C6, 0x71316, 0x7EB94, 0x7EE16` — то есть 4 пары
«начало/конец»: 0xD0000..0xD3BF8 и 0xEE876..0xEE878 (адреса программы,
файл = адрес − 0x80000), 0x712C6..0x71316 и 0x7EB94..0x7EE16 (смещения
калибровки). Арифметика по этим диапазонам не подтверждена — использовать
как подсказку, а не как спецификацию.

Переключатель проверки калибровочных monitor-сумм: `lc_swi_cal_mon_cks`
(XDF, оба файла определения) — `mmedaddress 0xE07`, то есть 0x70E07 в
512K-образе, 8 бит, «Set to 165 (0xA5) to disable». В стоке там `0x01` —
подтверждено на всех 18 образах 430069. Адрес 0x70E07 лежит **внутри**
cal-диапазона CRC (0x70000..0x72FFF), поэтому любая правка этого
переключателя требует пересчёта cal-суммы. Прочие «адреса отключения»
(0x70CE3, 0x70D7C, 0x70D7E, 0x70DA0, 0x70E0A) в стоках 430069 содержат
0x04/0x21/0xE7/0x00/0x5E — к переключателю они отношения не имеют, не
использовать.

## 5. Расхождения в корпусе (все разобраны)

Полный отчёт — `MS43/checksums/CRC_VERIFY_RU.md`, причины продублированы в
`KNOWN_ANOMALIES` (`MS43/tools/checksum.py`) и в тестах.

1. `Siemens_MS43_MS430069_E39_M54B25_EU4_LHD.bin` — **cal**.
   Отличается от E46-собрата `…E46_M54B25_EU4_LHD.bin` ровно тремя байтами:
   0x70AB1, 0x70B1A, 0x70B1E; хранимая сумма (0x5ADF) осталась от исходной
   калибровки. Это community-порт (см. `MS43/README.md`): правки внесли без
   пересчёта CRC. Файл нельзя считать эталонным стоком для границ политики,
   пока не выяснена природа этих трёх байт; перед записью в ЭБУ — пересчёт.
2. `E39_525__b137b56g_Ca430037_2.5L_Stok.bin` и его побайтный дубликат
   `E53__E39_b137b56g_Ca430037_2.5L_Full_Stok.bin` — **prog**, хранимая 0x06C1,
   расчётная 0xF63D при init 0x3031 (поле @ 0x6FFB6 = `10`).
3. `E39_525__b137b57g_Ca430037_Stok.bin` — **prog**, хранимая 0x0830,
   расчётная 0xF294 при init 0x3033 (поле @ 0x6FFB6 = `30`).

В файлах 2–3 содержимое prog правили после расчёта CRC (либо меняли поле кода
прошивки, либо код). Для 430037 остальные 512K-образы (E39 530i b137j54g,
E46 330i b137954g) сходятся полностью.

## 6. Грабли и правила

* Порядок правок по вики: сначала аддитивная сумма, потом CRC16. У нас
  пересчитывается только CRC16; `_mon` не трогаем вообще.
* Правка любого байта внутри сегментов ломает соответствующую CRC — это
  ожидаемо, пересчёт обязателен (и именно поэтому `repair_image` пишет только
  позиции сумм и перепроверяет результат).
* Не путать алгоритмы: в образе есть и forward-таблица 0x1021 (по смещению
  0x6DEFE) — к трём проверяемым записям она отношения не имеет; рабочий
  полином отражённый (0xA001).
* Bypass-патч калибровочных сумм ([PATCH] Checksum Bypass в community
  patchlist) отключает проверку cal-сумм, но **не** отменяет boot/prog —
  вики прямо предупреждает, что при этом всё равно нужны корректные boot и
  prog. Наш инструмент bypass-патч не ставит: мы считаем суммы.
* 64K-чтение калибровки нельзя проверять «как 512K»: запись лежит по 0x3FE0
  и адреса сегментов отсчитываются от 0x70000.

## 8. Воспроизведение

```bash
# проверка одного образа
python3 MS43/tools/checksum.py MS43/firmware/Siemens_MS43_MS430069_E46_M54B30_EU4_LHD.bin

# проверка всего корпуса с отчётом
python3 MS43/tools/checksum.py MS43/firmware/*.bin MS43/firmware_archive/*.bin \
    MS43/firmware_archive/*.Bin --report MS43/checksums/CRC_VERIFY_RU.md

# пересчёт сумм (пишет только позиции CRC, потом перепроверяет)
python3 MS43/tools/checksum.py вход.bin --out выход.bin

# тесты
python3 -m unittest discover -s MS43/tests -t .
```
