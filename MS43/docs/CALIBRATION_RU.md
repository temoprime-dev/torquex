# Ядро патчинга MS43 (`MS43/tools/calibration.py`)

Пункт 4 задания: «ядро патчинга → генератор → Stage 1/2 → хлопки/лимитер/launch →
наряд → тесты → русские документы». Этот документ — про ядро: оно пишет
калибровку в полный образ MS430069 строго по allowlist и доказывает, что не
тронуло ничего лишнего. Тесты — `MS43/tests/test_calibration.py` (27 штук).

## 1. Принципы

* **default deny** — символ пишется только если он есть в
  `MS43/policies/stage_policy.json`; символа нет — отказ.
* **только калибровка** — адреса 0x70000..0x7FFFF; код, загрузчик и
  идентификация (UIF/ISN/VIN) не пишутся никогда.
* **сначала патчи, потом калибровка** — дефолты из `[DATA] …` патчей
  (например `[DATA] LC & RAL Default Values` пишет 0x71316..0x71323) не должны
  затирать то, что просил клиент.
* **исходник обязан быть целым** — до планирования образ должен пройти все свои
  CRC-записи; «подозрительный» образ не правится, а отклоняется.
* **после записи — доказательство** — CRC пересчитывает наше ядро
  (`MS43/tools/checksum.py`), затем пост-проверка убеждается, что изменились
  только запланированные байты и позиции сумм.
* **ничего не выдумываем** — все числа приходят от вызывающего (генератора),
  в том числе из логов/стенда; ядро только проверяет и пишет.

## 2. Конвейер

```
запросы (символ → значения)
  → plan_changes()      проверки: allowlist, границы, точность, Δ, лимит ячеек,
                        монотонность, requires_patch, пересечения, CRC исходника
  → apply_plan()        патчи (patches.apply_patches) → байты калибровки
                        → пересчёт CRC (checksum.repair_image) → пост-проверка
  → PatchResult         образ + sha256 + список ячеек/патчей + изменённые CRC
```

План — это данные (`PatchPlan.as_dict()`), он пишется в JSON и попадает в наряд:
по каждому символу видно группу, источник (`source`), заметку (`note`),
`requires_patch` и каждую ячейку «до → после» с ошибкой квантования.

## 3. Что проверяется (коды находок)

| код | смысл | уровень |
|---|---|---|
| `SYMBOL_NOT_ALLOWED` | символа нет в политике | reject |
| `READ_ONLY` | символ помечен «только чтение» (модель момента, MAF-hack, CAN) | reject |
| `PATCH_REQUIRED` | символ фичи без применённого патча (поле `requires_patch`) | reject |
| `VALUE_NOT_REPRESENTABLE` | значение не влезает в сырое поле | reject |
| `QUANTIZATION_TOO_COARSE` | ошибка квантования больше `max_quantization_error_percent` (1 %) | reject |
| `POLICY_RANGE_VIOLATION` | вне `min..max` политики | reject |
| `DELTA_TOO_LARGE` | шаг больше `max_delta_percent` от текущего значения | reject |
| `TOO_MANY_CELLS` | правок в символе больше `max_cells_per_patch` | reject |
| `NOT_MONOTONIC` | таблица с `require_monotonic` перестала быть монотонной | reject |
| `CELL_COUNT` / `REQUEST_INVALID` | не тот размер списка/запроса | reject |
| `DUPLICATE_SYMBOL` | символ запрошен дважды в одном пакете | reject |
| `OVERLAPPING_WRITES` | две правки пишут в один байт | reject |
| `SOURCE_CRC_INVALID` | исходный образ не проходит свои CRC | reject |
| `IMAGE_SIZE` | не полный образ 512 КиБ (для 64 КиБ чтения — с версией в тексте) | reject |
| `CAL_VERSION_UNSUPPORTED` | версия калибровки не покрыта политикой (или не прочитана) | reject |
| `PATCH_UNKNOWN` / `PATCH_NOT_OFFERED` / `PATCH_DECLARATION_MISSING` / `PATCH_CONFLICT` | ворота и конфликты патчлиста | reject |
| `NO_CHANGE` | значения уже такие, как просили | warning |
| `NOTHING_TO_DO` | пустой план (ни правок, ни патчей) | reject |

План со **статусом `REJECTED`** не применяется: `apply_plan` его не примет.
План привязан к исходнику по sha256 — подсунуть другой образ нельзя.

## 4. CLI

```bash
# только посмотреть, что будет (ничего не пишет)
python3 MS43/tools/calibration.py --image MS43/firmware/Siemens_MS43_MS430069_E46_M54B30_EU4_LHD.bin \
    --set "id_n_max_mt__gear=7000,7000,7000,7000,7000,7000" --set c_vs_max_hys=6 --dry-run

# с патчем фичи: LC на 4000 об/мин, RAL по педали 60°
python3 MS43/tools/calibration.py --image <сток>.bin \
    --patch "[PATCH] Launch Control & Rolling Anti Lag" \
    --set c_n_max_lc=4000 --set c_vs_max_lc=30 --set c_conf_ral=1 --set c_pvs_min_ral=60 \
    --out /tmp/stage.bin --json-out /tmp/stage_plan.json
```

* `--set СИМВОЛ=знач1,знач2,…` — полный список ячеек таблицы; `None` (или `-`)
  оставляет ячейку как есть; для одиночной константы можно одно значение.
* `--policy` / `--catalog` — свои файлы политики и каталога патчей (для тестов).
* `--acknowledge` — подтверждения уровня генератора (`acknowledge_risk`,
  `acknowledge_oil_pump`); ядро их записывает в план и наряд, а решение об их
  обязательности — за генератором (`ALLOWLIST_RU.md` §3).

Выход: `0` — записано и проверено, `2` — отказ с печатью причин.

## 5. Пример полного прогона

```
план: PLANNED | образ 524288 байт | sha256 513b69bcd31f2d8d… | политика v1
  патчи: [PATCH] Launch Control & Rolling Anti Lag
  c_n_max_lc [patch_lc] ячеек 1 (+патч [PATCH] Launch Control & Rolling Anti Lag)
     [0] 0x7131B: 8160 -> 4000 (сырое 255 -> 125, ошибка 0.000%)
записано: /tmp/cal2.bin (sha256 e2c0efc248c08ca0…, ячеек 4, байт 6)
  CRC cal @0x73FE0: 0xE966 -> 0xC301
```

На стоке `c_n_max_lc` = 0xFF (8160 об/мин — «не задано»/максимум), поэтому
первый же запрос LC заменяет его на реальное значение, а вместе с ним приходят
`c_vs_max_lc`, `c_conf_ral`, `c_pvs_min_ral`: генератор пишет весь блок LC/RAL
целиком и печатает его в наряде.

Через `python3 MS43/tools/checksum.py /tmp/cal2.bin` видно, что сошлись все три
записи (boot/prog/cal), а boot и prog суммы не изменились — патч в этом примере
калибровочный, программную часть не трогает.

## 5a. Защита по версии калибровки

Адреса, границы и стоки политики сняты только с 18 образов **MS430069**
(`MS43/firmware`), поэтому ядро первым делом читает код версии из строки
идентификации — ASCII `4300xx`:

* полный образ 512 КиБ — по смещению `0x70008`;
* 64 КиБ чтение калибровки — по смещению `0x8`.

Если версии нет в реестре политик, план получает `CAL_VERSION_UNSUPPORTED` и
статус `REJECTED` **до** проверки CRC и до планирования правок: `apply_plan`
такого плана не примет, а `patches.apply_patches`/`revert_patches` отказываются
сами. 64 КиБ чтение отклоняется кодом `IMAGE_SIZE` с прочитанной версией.
Проверки живут в `calibration.check_version_supported` (по реестру версий) и
`calibration.check_cal_version` (для конкретной политики); `stages.build` зовёт
их первым делом.

Политик теперь несколько — по одной на версию, и ядро выбирает свою по коду
версии из образа (`policy.resolve_policy`). Реестр — `VERSION_POLICY_FILES` в
`MS43/tools/policy.py`:

| версия | файл политики | символов | определение-источник адресов |
|---|---|---|---|
| 430069 | `policies/stage_policy.json` | 97 (63 XDF + 34 патчлиста) | `Siemens_MS43_430069_Extended_Load_512K.xdf` |
| 430056 | `policies/stage_policy_430056.json` | 63 (только XDF) | `MS430056_Extended_Load_512K.xdf` |
| 430037 | `policies/stage_policy_430037.json` | 62 (нет `ip_iga_tqr_amt__n__maf`) | `MS430037_Extended_Load_512K.xdf` |
| 430055 | `policies/stage_policy_430055.json` | 63 | `MS430055_Extended_Load_512K.xdf` |
| 430066 | `policies/stage_policy_430066.json` | 63 | `MS430066_Extended_Load_512K.xdf` |
| 430064 | нет | — | полного стока нет: адреса доказать не по чему |

Почему переносить адреса одной версии на другую нельзя — видно по тем же байтам
(проверено на `MS43/firmware_archive` и определениях версий):

| версия | что лежит по адресу 430069 `0x70BE8` | свой адрес `c_n_hys_max_puc` и его байт | `ip_iga_puc__n__tco` (адрес, начало) |
|---|---|---|---|
| 430037 | `07` | 0x70B03, `0F` | 0x77180, `7D 76 6E 2D 2A` |
| 430055 | `01` | 0x70B81, `0F` | 0x76FDF, `48 45 43 41 42` |
| 430056 | `00` | 0x70B83, `0F` | 0x76FED, `8E 8B 87 81 7E` |
| 430066 | `78` | 0x70BEF, `14` | 0x77179, `2F 30 30 32 41` |
| 430069 | `0F` | 0x70BE8, `0F` | 0x7717D, `2D 28 23 1F 2F` (ПХХ ≈ −6.75°) |

Первая колонка — прямое доказательство запрета на перенос: один и тот же
абсолютный адрес в образах разных версий держит разные данные (`07`, `01`, `00`,
`78`, `0F`). Вторая — адрес объекта **этой** версии из её определения; байт `0F`
у 037/055/056 — то же значение, что у 069, но лежит **в другом месте** (и у 066
даже значение иное: `14`).

Заметно и обратное: у 430069 и 430066 таблицы совпадают по содержимому, но
**адреса всё равно разные** — поэтому «похожесть» версий не повод переносить
адреса. Доказательства адресов по каждой версии (второе определение 64 КиБ —
274/274, поиск таблиц по содержимому, согласие одного датасета 512 КиБ/64 КиБ
55/55, стоки в границах) собраны в `docs/VERSION_COVERAGE_RU.md` §2.

Читать версию умеет и `checksum.read_cal_version` (та же логика, ядро CRC).
Покрытие расширяется только **отдельной политикой на версию**: адреса из
определения этой версии, границы из её стоков, свой набор символов, отдельные
тесты (`python3 MS43/tools/policy.py --build-all`). 64 КиБ чтения патчить нельзя
вообще: в них нет boot/prog и полного набора записей CRC, ядро говорит об этом
кодом `IMAGE_SIZE` и показывает прочитанную версию.

## 6. Границы применимости

* **boot/prog CRC**: если план меняет только калибровку, меняется только
  cal-CRC; ядро не предполагает этого, а проверяет — и показало, что так и есть.
* **`_mon`-суммы** (0x6FDAE, 0x72FFC) — runtime, статически не проверяются и не
  пересчитываются (см. `CHECKSUM_RU.md`): это статус `unverified` в отчёте.
* **Монотонность** проверяется в порядке хранения байтов в файле (для
  одномерной кривой ДМРВ это и есть порядок значений) — только там, где
  `require_monotonic = true`.
* **Аномальный образ** `E39_M54B25_EU4_LHD` (не сходится cal-CRC) ядро
  отклоняет — тест это фиксирует.
* Ядро не решает продуктовых вопросов: «выше стока → `acknowledge_risk`», «выше
  6750 → `acknowledge_oil_pump`», «хлопки только без катализатора», «Stage 2
  привязан к железу» — это генератор (`ALLOWLIST_RU.md` §3).

## 7. Тесты (27)

`MS43/tests/test_calibration.py`: отказ по неизвестному символу, read-only,
`requires_patch`, границам, точности, Δ, лимиту ячеек (синтетическая политика),
монотонности, дублям, пересечениям, битому CRC источника, пустому плану;
применение меняет только ячейки и CRC; патч-онли план побайтово совпадает с
`patches.apply_patches`; конфликтные патчи отклоняются; план нельзя применить к
другому образу; все 18 стоков принимают stage-подобный план (кроме известной
аномалии E39, для неё проверяется отказ); CLI dry-run/apply/JSON.
